---
name: maalc-live-test
description: Run maalc against the MuMu emulator or the PC client's window and report it with evidence. Use for a live test, an experiment, live verification of a PR, or an unattended run on the emulator.
---

A **live test** drives the user's real game account. It owns the emulator alone, starts from a known screen, and leaves the account, the game settings and `install/` as it found them. Emulator settings (resolution, window) stay the user's. Machine-local state lives in `.local/` of the main checkout, never of your worktree (`docs/agents/local-dev.md`); `install/` is the main checkout's too.

The tools are in `tools/live/`, each with its options in `--help`. Reach for them before writing a script:

| Tool | Does |
| --- | --- |
| `queue.py` | the emulator and bench tickets, `wait --resource <bench|emulator> --name <ticket>` blocks until one ends and exits with its code (75: still running, run it again; give the ticket's `run` a `--log` so `wait` prints it), `pause` a hold, `detach`, `status`, `resume` |
| `preflight.py` | `screen` names the emulator's screen before costly prep; `plan` checks a run in progress; `recording` notes a stretch with no new frames |
| `backup.py hold` | backs up `install/` and verifies it after the run |
| `bot.py` | `run` the bot headless through the install's runner (`runner/`, the one the settings window uses) into a stamped `run.log`, each task on the options of the install's settings file; `prep` a test install's settings file, the task options too (`--set run.runs=1`); `awake` keeps the screen on |
| `device.py` | `shot`, `tap`, `key`, `start` or `restart` an app; `freeze` the bot on a log line to look or act, then resume |
| `give_way.py` | a run that holds the emulator gives way to the daily task: `watch` stops the bot on the map, goes to the main window with the dungeon in progress, queues the next leg behind the daily and ends the hold; `--now` is a deliberate break under the same hold; `look` names a capture's screen |
| `giveup.py` | `run` ends a Mirror Dungeon run early from a battle: Give Up, Forfeit, GiveUpRewards, never Claim; `look` names a capture's screen |
| `evidence.py` | `events`, `steps`, `frames`, `clip`, `clips` (a run's annotated clips from one JSON spec, local paths boxed out), `mask` (`--box` for a local path); `map` and `packs`, the route and pack evidence of step 8 |
| `gui_run.py` | a run from the settings window ("From the settings window" below): `open` the window on an install as it is, retitled; `record` one window only, or wait for it; `start`, `stop` (on a run-log line), `state` over DevTools; `windows` and `title` |
| `maafw_events.py` | maafw.log touches as events.json |
| `maafw_loaded.py` | given the PID of what runs the tasks (the settings window, or the runner `bot.py run` starts): the Maa DLLs it and its agent have loaded, and whether its MaaFramework.dll is the fixed one |
| `map_taps.py` | every touch on the Mirror Dungeon map (follow, a full read's take, `find_bus` and the other drags) as a CSV row: taken or ignored by `recovery.same_screen`, seconds since the map faded in, the log line it led to; a summary per kind and verdict |
| `dialogs.py` | the game's confirm dialogs, to diff against the pipeline before an unattended run |
| `memwatch.py` | the bot's (or the settings window's) process tree sampled until it ends: a CSV row per process (role runner, agent, window or other; working set, private) and the peak and last per role, the memory half of a performance fix's before/after |

Log statistics: `tools/wait_spans.py` (Now Loading and other waiting screens), `tools/maafw_timeline.py` (time per node), `tools/video_align.py` (a recording against the log, its drift and freezes). A one-off script none of these covers goes in `<local>/scratch/<task>/`; `docs/agents/live-tools-inventory.md` lists which old scripts the tools replaced.

Recording and annotation come from two global skills: `screen-record` and `evidence-annotate`. Read each before its step.

Resolve the main checkout's `.local/` once, before starting a process: `uv run python -c "import sys; sys.path.insert(0, 'tools'); from local_dir import local_dir; print(local_dir().as_posix())"` (from any worktree), and write the printed absolute path wherever the steps say `<local>`. A relative `.local/...` in a command run from your worktree lands in the worktree's own `.local/`, which `queue.py resume` and `pause` never read (`queue.py:406`). New probe scripts and cache go in `<local>/scratch/`; `.local/probe/` holds the migrated historical scripts, environments and captures. See `docs/agents/local-dev.md` before migrating or removing old compatibility paths; another task's recording must finish first.

## Steps

0. **Resume.** Whenever your turn (re)starts, including after a rate limit, an error or a "continue" message, run `uv run python tools/live/queue.py resume --task <task>` first and act on its `next:` line; never re-arm a wait for a bot that already ended (it finishes the run while no agent watches, and the recording and the emulator stay held). Done: you know whether hold and bot run, whether `done` exists, and which step is next.
1. **Queue.** Use a fresh `<task>` name each run (its `<local>/scratch/<task>/` folder holds the logs `resume` and `status` read). Take the emulator with the one non-interactive command, detached so it outlives the harness (which kills a background command after 2 hours): `uv run python tools/live/queue.py detach --log <local>/scratch/<task>/hold.log -- uv run python tools/live/queue.py run --resource emulator --name <task> -- uv run python tools/live/backup.py hold --label <task> --done <local>/scratch/<task>/done --timeout 7200 --guard '<local>/scratch/<task>/bot*.log' [--stop-recording <screenrec profile>]`. The glob takes in every bot run of the hold (`bot.log`, then `bot-b.log`, ...), so a second run keeps the timeout and the recording going. With the flag, `hold` stops that recording once, 60 s after the bot ended, so a run nobody watched does not leave it growing, and logs `[hold] stopping recording`; it logs `[hold] bot ended <time>` either way. Taps of your own after a bot ended check the recording first (step 5). `queue.py status` marks a holder whose bot ended over 10 min ago with no `done` file as waiting for the agent. The detach returns at once with a pid. Without a `done` file `hold` gives up after `--timeout` (required, no default), counted from the end of the bot of step 6 (`--guard`), never while it runs or while the task is paused. To pause a run (the user says stop, a rate limit, a long wait), run `queue.py pause --task <task> [--minutes N]` before you kill the bot, not after: a hold whose bot died times out and hands the emulator to the next ticket while you still drive it. `queue.py status` shows a paused holder as PAUSED and a hold under 30 min from its timeout as "expires in N min"; `pause --task <task> --end` lifts it. `hold` backs up `install/` (an md5 manifest and a copy of `settings.json`), waits until the `done` file exists, then verifies `install/` against the backup. The queue is first-come-first-served, except the daily task's `FIRST` ticket (step 6), and drops dead holders; while another task holds the emulator you wait on `hold.log` with one Monitor until-loop (re-arm it if it times out; the hold keeps its place), so keep your turn open. Steps 2, 5, 6 and 8 are your own actions, taken while the command holds the emulator. Done: `hold.log` shows `[queue] start <task>` and `backed up <n> files`.
2. **Pre-flight.** Right after step 1 and before any pytest, install rebuild or other costly prep (a game update found after 21 minutes of prep cost a run): `uv run --group probe python tools/live/preflight.py screen --shot <local>/archive/<date>-<topic>/00-start.png`. `ok` → go on. `accept` (an update, download or User Agreement dialog) → go on (the user's decision of 2026-10-21); the bot's nodes accept it when `run.auto_download` / `run.auto_accept_terms` are on. `stop` (a resumable Mirror Dungeon run, an outdated client, any other screen; exit 1) → stop and ask; forfeiting or continuing a run is the user's call and never goes through Queue. Done: `preflight.py screen` printed `ok` or `accept`.
3. **Scope.** Run the segment each check needs (a few decisions), not a whole dungeon, unless the brief names a full run. Done: every check in the brief names the segment that exercises it.
4. **Settings.** Write down every game setting you will change (a manual x3 battle speed does not persist between runs; set it again), with its value now, in `<local>/scratch/<task>/settings.md`. Done: the file exists.
5. **Record.** `screen-record`: `screenrec.py start --window <title substring> --height 720 --out <local>/archive/<date>-<topic>/ [--profile <name>] [--crop-top N] [--keep-gb N]`. Always pass `--height 720`: without it the clip has the window's own size (about 1400p, 11 Mbps), which piled up 62 files and 171 GB on 2026-10-29, and MaaFramework reads the screen at 720p anyway. A live 720p HEVC recording measured about 5.4 Mbps, so budget about 2.4 GB an hour (#34's ten runs: 24.14 GB over 35,785 s before the re-encode; the 2026-11-12 prep run: 1.73 GB over 2,556 s, `ffprobe`); the archive later re-encodes long recordings to CQ 28, about 2.2 Mbps (#34's archive INDEX row), which is not what the recorder writes. The x264 fallback is larger. A run that may outgrow its budget passes `--keep-gb` above its expected size (`--keep-gb` prunes the oldest `rec_*.mp4` in `--out` only). To keep a recording under `<local>/archive/recordings/`, make a hard link (`New-Item -ItemType HardLink -Path <local>/archive/recordings/<name>.mp4 -Target <rec>.mp4`), never a copy. It stays only while some folder still links it or an `INDEX.md` row naming the file has an open issue: `prune` deletes an older one that has neither (`docs/agents/local-dev.md` "Keeping disk space"). What `start` refuses and what it only warns about is in `screen-record` step 1. Pass the same `--profile` to `status` and `stop` as to `start`. The recording is **always on**: one recorder, started here, running until step 7 or `hold --stop-recording` stops it (the user's decision of 2026-11-05). The one exception is a brief whose run settings say `recording | no`, which the coordinator passes to `brief.py` only when the user asked for a run without a recording (2026-11-07); under it, device screenshots stand in for the recording here and in steps 7, 8 and 10. Taps of your own may follow a bot that ended (a Forfeit, GiveUpRewards, the taps before the next bot run). Before the first of them, under `--stop-recording` wait until `hold.log` shows `[hold] stopping recording`, then run `screenrec.py status [--profile <name>]`; without `active True`, `start` a new file with the same arguments, then tap (2026-11-06: the first tap came 13 s after the bot ended, and the stop at 60 s left Defeat through GiveUpRewards unrecorded). The window draws no new frame when the game freezes as well as when the display sleeps, so a still file is a fact to report, not a broken recording. 20 s in, and again a few minutes into the run, `uv run python tools/live/preflight.py recording --out <out>` checks the recording in progress (exit 1 only when no recorder runs: start one). Append each `note:` line it prints, and each `warning:` line of `screenrec.py` with the time you saw it, to `<local>/scratch/<task>/recording.md` while the run and the recording go on. `bot.py awake` keeps the screen on. Done: `screenrec.py status [--profile <name>]` prints `active True`, `preflight.py recording` exit 0, and `recording.md` holds every such line.
6. **Run.** Start the bot the way the brief says, through `uv run python tools/live/queue.py detach --log <local>/scratch/<task>/bot.log -- <bot command>` (the `--guard` of step 1), never as a plain background command; it prints the pid. Within a minute run `uv run python tools/live/preflight.py plan --log <local>/scratch/<task>/run.log`: it exits 1 when the log has no `new run:` line or says `no run plan in memory`, which means the bot took over a leftover run (its weekly bonuses and Modules were not planned); stop the run tree and ask. A later bot run in the same hold goes under its own `bot-<x>.log`, which the guard's glob follows. Before such a later run, and when a run ends, run `uv run python tools/live/queue.py status --resource emulator`: a waiting ticket marked `FIRST` is the daily task, which the 05:00 game reset ends (#465), or the next leg of a run that gave way to it. Let it in at the first point with no Mirror Dungeon run in progress (a run that resumes the dungeon goes on first, or the daily's own pre-flight stops at it): do steps 7 and 9 first and step 8 after (it needs no emulator), then take a fresh `<task>` through steps 1-5 for the next run; step 10 lists both tasks' recordings. Never stop a running bot for it, unless the brief says the run gives way to the daily ("Giving way to the daily" below). The bot command is `uv run python tools/live/bot.py run --install <install> --log <local>/scratch/<task>/run.log`; step 8 reads `run.log`. Its tasks read their options from the install's settings file, which the brief's `bot.py prep --set` sets (`run.*`, `luxcavation.<task>.*`, `charge_enkephalin.count`, #813). Wait with one Monitor until-loop on `uv run python tools/live/queue.py status --log <local>/scratch/<task>/bot.log` (exit 0 running, 1 ended); a Monitor that times out ends only the wait, so re-arm it. Your turn stays open until the run ends. Done: the run ended or hit the brief's time limit.
7. **Stop.** `pwsh tools/live/stop_run.ps1 -RunPid <pid>` takes the whole process tree; then `screenrec.py stop [--profile <name>]`. Done: `stop_run.ps1 -WhatIf` lists no process, and `stop` printed `saved <file>.mp4` with its `started` time, which is step 8's `--start` exactly (frames carry their wall-clock capture time; no `--offset` needed). If `hold` already stopped the recording (`--stop-recording`), take that file's `saved` and `started` from the `hold.log` output of that stop; `stop` ends the file step 5 started after it, if any, and step 8 takes every file.
8. **Evidence.** Everything leaves `.local/` masked by `<local>/evidence/masks.json`, which blacks out the three identity regions: the player-number plate, the player name above the LV panel at the bottom left (36,626,98,20 in game pixels) and the account e-mail; `evidence.py` applies it to every still and clip it writes. Below, every command runs as `uv run --group probe python tools/live/evidence.py`, `<rec>` is `--video <mp4>@<started>` from step 7 (one per piece of a run recorded in pieces) and `<out>` is `<local>/archive/<date>-<topic>/`.
   - **Route, every floor played**: `map <local>/scratch/<task>/run.log <rec> --floor N -o <out>/f<N>/route --clip` writes `stitched.png` (the whole floor from the frames before and after each drag, every node the bot read boxed with its type and Cost, special reads (boss by glow or shop, Cost miss, retyped) in their own colour with a legend, the route numbered), `before-1.png`, `after-N.png` and `drag-clip.mp4`. Judge each node of `stitched.png` against the frames: a wrong type, a wrong Cost or a node the bot did not list goes into a FIX file (its form is in `evidence.py --help`), and a rerun with `--fix FIX.json` marks it red or orange. A floor read again after a restart: the same command with `--after <time of the restart line>`.
   - **Packs, every floor played**: `packs <local>/scratch/<task>/run.log <rec> --floor N -o <out>/f<N>/packs --clip` writes a `pack-K.png` per reading, refreshes included (each card's name and weight, the pulled card's thick border, the seconds from the deal to the cards standing still), and `pack-K-clip.mp4`.
   - **Other checks**: `events` and `steps` turn `run.log` into evidence-annotate's events and captions (`maafw_events.py` reads a maafw.log, the main checkout's), then `evidence-annotate`: `annotate.py VIDEO -o OUT --start <started> --events events.json [--steps steps.json] --masks <local>/evidence/masks.json [--from T --to T] [--frames T,…]`. A device screenshot goes through `evidence.py mask` before it is shared.
   - **Post**: each floor's route stills and drag clip to #251, its pack stills to #252 (`gh issue comment <n> --attach '<file>#<alt>'`), or to the PR the run verifies. Add one row to `<local>/archive/INDEX.md`.

   Done: every check of the brief has its annotated clip; each floor played has a `stitched.png` with every node it read boxed and judged, a drag clip and a `pack-K.png` per pack reading, posted to #251 and #252 (or the PR); the INDEX row exists.
9. **Restore.** Game settings back as written down in step 4; read each one back on the screen and list it in the report as `restored: <setting> <value>`. Then create the `done` file of step 1 (the Write tool). `hold` verifies `install/` and the queue command ends. Done: `hold.log` ends with `install matches the backup (md5)` and `queue.py status --log <local>/scratch/<task>/hold.log` says `ended`.
10. **Report.** Per check: pass / fail / not reached, with its clip. Every recording file of the run, with its `started` time. The lines of `recording.md` (step 5), with their times. Acceptance numbers: met or not met. Upload clips and frames with `--attach` (AGENTS.md "Public repo"); a failure opens an issue with its evidence attached.

Done: every check has a verdict and a clip, every tap of your own falls inside a recording file (under `recording | no`: a still for each), the INDEX row exists, `hold` matched, and the queue holds no ticket of yours.

## From the settings window

A check of what the settings window does with a run (Start, Stop, a task's state, the window starting MuMu) runs the bot from the window instead of `bot.py run`. Steps 0-4 and 8-10 above stay; W1-W5 here replace steps 5-7. `gui_run.py --help` has every option; `docs/agents/gui-driving.md` says when a click goes through cua instead.

- **W1 Install.** A worktree's own: build the window (`docs/agents/gui-driving.md` "Build and launch"), then `uv run python tools/install.py --release` builds `<worktree>/install/` with it, then `uv run python tools/live/bot.py prep --install <worktree>/install [--set tasks.ClaimMail.enabled=true ...]` copies the user's settings and sets the brief's (a task the brief leaves out: `--set tasks.<id>.enabled=false`). `gui_run.py open` refuses the main checkout's `install/`: Start saves the settings file. Done: `prep` printed the keys it set.
- **W2 Open.** `uv run python tools/live/queue.py detach --log <local>/scratch/<task>/gui.log -- uv run python tools/live/gui_run.py open --root <worktree>/install`, with the hold of step 1 (Queue) guarding `'<local>/scratch/<task>/gui*.log'` (the window runs the bot). It starts the install's own window on its own settings (`gui_devtools.mjs open` would lay the folder out again with demo settings), with a DevTools port and a WebView2 folder of its own, and renames the window from "maalc" to `maalc-live-<port>`: screen-record takes the largest window whose title holds `--window`, and "maalc" alone is in the editor's, the agent's and the user's own settings window's titles. Done: `gui.log` shows `{"pid", "hwnd", "port", "title", ...}`; the hwnd is cua's `window_id`.
- **W3 Record.** The window: `uv run python tools/live/gui_run.py record --hwnd <hwnd> --out <out> --profile gui`. The emulator: `... record --window "Android Device" --crop-top 60 --out <out> --profile default`, and when the run is to start MuMu, add `--wait 600` and start it in the background before Start: it records from the moment the window appears. `record` refuses when more than one visible window matches, and stops a recording that took another window. The settings window draws a frame only when its page changes, so screen-record's no-frame warnings on `gui` are expected; note them in `recording.md` as step 5 (Record) says. Done: `record` printed `{"recording": <hwnd>, ...}` for each.
- **W4 Run.** `uv run python tools/live/gui_run.py start --port <port>` presses Start (it refuses while Start is disabled, and says why); a check of the click itself goes through cua. `state --port <port>` prints the status line, the phase and each task's state; `state --until ended --timeout <s>` waits for the run's end. To stop at a moment, `stop --port <port> --root <worktree>/install --on "<log text>" [--delay S]` waits for the line in the run's log (`<install>/logs/runner/run-*.log`) and presses Stop; start it in the background before Start and press Start once it prints `{"watching": ...}`, or start it once the run is under way. The run log is step 8's LOG. Done: `state` shows the phase `ended` and each task's state.
- **W5 Stop.** Stop the holder by the pid in `gui.log.pid` (`taskkill /T /F /PID <pid>`): the window and its WebView2 end with it. Then `screenrec.py stop --profile gui` and `--profile default`; each `saved` and `started` is a `--video` of step 8. Done: `gui_run.py windows maalc-live` lists no window, and each `stop` printed `saved`.

Evidence for a check of the window: `evidence.py clips <spec> -o <out>/clips` cuts every check's clip from one JSON spec (its form is in `evidence.py --help`): the settings window's clips with `boxes` over its local paths (the header, the run log's start line, the MuMu fields), the emulator's with the run log for its touches. A still of the page: `node tools/gui_devtools.mjs still <png> --port <port> --mask "header .path"`; any other still with a local path: `evidence.py mask <png> --box X,Y,W,H`.

## Giving way to the daily

A run of several hours whose brief says so (#853) gives way to the daily task in the middle of a dungeon and goes on with the same run after it. Steps 0-10 stay; G1-G3 add to them. The run's game settings of step 4 stay as they are for the daily and are restored at the end of the last leg, so a run that changes one the daily must not see does not give way.

- **G1 Watch.** Right after step 6 started the bot: `uv run python tools/live/queue.py detach --log <local>/scratch/<task>/give-way.log -- uv run --group probe python tools/live/give_way.py watch --task <task> --next <task>-b --install <install> [--recording <profile>]`, `--recording` as the hold's `--stop-recording`. Wait for the run with one Monitor that ends when either log ends (`queue.py status --log` of bot.log and of give-way.log). Done: `queue.py status --log <local>/scratch/<task>/give-way.log` says running.
- **G2 After it ended.** Its last line in give-way.log says what comes next (`give_way.py --help` lists the endings). `stop:` the bot still runs: start the watch again. Gave way: the recording is stopped and `done` exists; its `[hold]` and screenrec lines hold the file's `saved` and `started` for step 8. Failed: the hold is paused and the emulator is yours; look at `give-way/*-failed.png`, and bring the game to the main window, or ask; the dialog "The previous session has expired" is only the user's to answer. The watch closes the Event / System Notifs window over the main window by itself, with the Back key (`give-way/*-notice-<n>.png` and `*-notice-<n>-after.png`), and no other window. The bot ended by itself with the daily waiting: steps 7 and 9 let the daily in; with no daily waiting, the run goes on as without it.
- **G3 The next leg.** `<task>-b` already waits behind the daily: do not queue it again. Wait for `[queue] start` in `<local>/scratch/<task>-b/hold.log`, then steps 2, 5 and 6 under `<task>-b`: the same install and no new `prep` (the settings of the run in progress stay), `preflight.py plan --resumed --within 600` in place of `plan`, and G1 again with a fresh `--next`. Done: `plan --resumed` printed `ok`, and the floor the log names next is the one the first leg stopped on.

A deliberate break, to check that Resume picks the run up when no daily came: when `run.log` shows `floor <N> memory:` for the floor the brief names, end the G1 watch (`taskkill /T /F` on the pid in `give-way.log.pid`; two watches would both stop the bot) and run the same `watch` with `--now` in place of `--next` and `--recording`. The hold stays; then the bot again under `bot-b.log` with its own run log `run-b.log`, `plan --resumed` on that, and G1 again with `--bot-log` and `--run-log` naming the two. Check the recording first (step 5): under `--stop-recording` it stopped when the bot was away over 60 s.

## On the PC window

The PC client's window (Limbus Company on Steam, title `LimbusCompany`) logs in to the same account, so the `emulator` lane covers it: `docs/agents/local-dev.md` "The emulator lane" has the checks before a PC step and when the user plays. A tool's PC command is its `--device pc` (pc_shots.py has no other), and it acts only under a ticket of its own that holds the lane: `uv run python tools/live/queue.py run --resource emulator --name <task>-<step> -- <tool command>`; without one it prints `refused:` and touches no window. Step 1's hold is a ticket of the same lane, and a PC command's ticket would wait behind it until it ends, so a PC session takes no hold: its bot runs on a test install (W1's, or a copy under `<local>/scratch/<task>/`), never the main checkout's `install/`. The steps above change so:

| Step | On the PC window |
| --- | --- |
| 2 Pre-flight | `preflight.py screen --device pc --install <install>` under its own ticket: the window's screen named with the PC resource layer over base; an update notice is a `stop` (Steam updates the client, #944) |
| 5 Record | `screenrec.py start --window LimbusCompany --height 720` (or `gui_run.py record --window LimbusCompany`). How much of a windowed window's title bar `--crop-top` cuts is not measured yet: measure it on the first PC recording and write it here |
| 6 Run | `queue.py detach --log <local>/scratch/<task>/bot.log -- uv run python tools/live/queue.py run --resource emulator --name <task> -- uv run python tools/live/bot.py run --device pc [--pc-size 720\|900\|1080\|1440] --install <install> --log <local>/scratch/<task>/run.log`. `--pc-size` sets the client area for the run and the runner puts the window back after it; leave it at `keep` unless the brief names a size. This version's controller takes no input (spec #922 D6), so the run ends at the task's first tap with `the game's window did not take an input` (PcInputFailed); `tests/test_live_bot.py` dry-runs it on a fake window |
| 8 Evidence | the PC identity regions are not measured yet (`IDENTITY` in `tools/live/pc_shots.py`), and `<local>/evidence/masks.json` is the emulator's layout: no PC still or clip leaves `.local/` until they are measured (D15). `pc_shots.py mask` refuses until then. `maafw_events.py` reads no PC touches (none exist yet) |

The other tools on the PC window: `pc_shots.py` takes the shots of #941 (`info`, `compare`, `watch`). `device.py --device pc` takes `shot`, and `freeze` suspends the whole bot tree (no adb server serves the window) and runs its file's `shot` and `plan` lines. `tap`, `press` and `key` are refused until the controller takes input (#946), `start` and `restart` until #948, and so are `giveup.py run`, `ego_card.py open` and `give_way.py watch`, each with why.

## Asks the user first

Give Up on a battle, Claim (a reward) and the weekly bonus follow the brief's "Machine-local rules" (`tools/live/brief.py` appends them); without such a rule each asks the user first, as does starlight beyond the configured graces. The answer covers that one action.
