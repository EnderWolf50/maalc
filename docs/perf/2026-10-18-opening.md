# 2026-10-18 起手段落時間分析（#115）

唯讀分析既有 log，沒有動模擬器。範圍：每局從 `MirrorEntryNewRun` 到第 1 層 `ThemePack`（含 `PickThemePack` 動作）的每個 pipeline step。

## 資料與方法

- 來源：`install/debug/debug/maafw.bak.2026.10.17-*.log`、`maafw.bak.2026.10.18-03.21.39.12.log`（`maafw.log` 與最後兩份備份是別的測試，沒有完整的起手）。找到 12 段起手，其中 1 段（10-17 03:23）是沒有 GiftSearch 的舊版流程，扣掉；剩下 10 段，下面都是這 10 段的中位數。
- 方法同 `docs/perf/2026-10-17-run-profile.md`：
  - 一個 step = 相鄰兩個 `Node.PipelineNode.Succeeded` 的間隔，歸給後一個節點（間隔含「等它出現＋動作＋post_delay」）。
  - 自訂動作的時間取 `CustomAction::run` 的 enter／leave；「固定等待」= 動作內相鄰兩次 agent 呼叫（截圖、OCR、點擊）之間超過 0.2 秒的空檔，也就是 `tap(..., wait=)` 與 `time.sleep`。
  - 「post_delay」取 `assets/resource/base/pipeline/mirror_dungeon.json` 的值。
  - 「其餘」= step − 動作 − post_delay，是 MirrorHub 的輪詢（rate_limit）、辨識與遊戲轉場，這次沒有動。
- 分析腳本留在 主 checkout 的 `.local/probe/open/`（`find.py`、`prof.py`、`an.py`、`an2.py`），位於 gitignored 私有資料夾。
- 這批 log 是 #106 之前的版本，所以總長（中位數 54.8 秒，最短 52.4、最長 65.3）比 issue 寫的約 48 秒長；各步的相對大小一樣。

## 改法與預期省下的時間

固定等待一律換成「看下一個畫面」：`until()` 每 0.2 秒截圖到條件成立，逾時時間等於原本的固定等待，所以條件永遠不成立時不會比以前慢。新的共用函式 `tap_then(x, y, done, timeout)`（點一下、再 `until`）與 `shows(roi, pattern)`（OCR 比對），以及一個 pipeline 用的 `TapUntil` 動作（取代 Click ＋ post_delay）。

| 步驟 | 改成 | 預期省（秒） |
|---|---|---:|
| PlanRun | 按 Enter 後等「Will you enter」對話框 | 1.0 |
| MirrorEnterDialog | `TapUntil`：等入口頁讀到 `F n`（舊的 `Before Entry` 還在時 MirrorHub 會再規劃一次） | 1.0 |
| MirrorEntryPaused | `TapUntil`：等 `TEAMS` 清單或 Resume 對話框 | 1.0 |
| SelectTeam | 點隊伍後等標題變成 `TEAMS #n`；Confirm 後等等級警告或星光頁 | 2.3 |
| LevelWarning | `TapUntil`：等星光頁 | 1.2 |
| BuyStarlight | Enter 後等確認對話框 | 1.0 |
| ConfirmStarlight | Confirm 後等起始飾品頁 | 1.0 |
| PickStartingGift | 開關、櫃子（`still`）、飾品（Select n/m 改變）、Select（彈窗出現或頁面離開）；node post_delay 拿掉 | 4.0 |
| GiftGet | 改成自訂動作：點 Confirm，等彈窗消失或換成下一個飾品的彈窗（看名牌文字）；post_delay 拿掉 | 1.2（n 個彈窗時更多） |
| GiftSearch | 切分頁（`still`）、點飾品（面板的名單改變）、Select（等 Consume 對話框）、Confirm（等 GET 彈窗）、Refuse（等 Forgo 對話框）；node post_delay 拿掉 | 5.5 |
| PickThemePack 的難度 | 切換後等標籤換成目標難度再 `still`；讀不到時 `until` 取代 `sleep(1)` | 2.5 |
| **合計** | | **約 18–22** |

預期起手從約 54 秒（這批 log）降到約 32–36 秒；若 #106 之後的 48 秒是對的，則約 27–30 秒。這是估計，要實機驗證（見 PR）。

沒有改的：

- MirrorHub 的輪詢與辨識（每步 0.6–1.5 秒的「其餘」）、Loading、GiftGet 的遊戲彈出動畫。
- `GiftSearch.scroll` 的 0.5 秒彈回等待、`BuyStarlight` 買 Grace 時的 `tap` 預設等待與 `set_level`：這批 log 的隊伍沒有買 Grace、也沒有捲動，沒有數據，不動。
- 「n 個彈窗用連點一次關掉」：不確定遊戲是否接受，且 GiftGet 已經是「關一個、看到下一個就交回」，不再等固定時間，先不做。
- `PickThemePack` 的 Refresh（`wait=3`，只有三張都是 avoid 才發生）。

## 順手查到的：#73 觀測前的持有星光

`runs.jsonl` 的 `owned_before` 比開局前的畫面多 60（1542 對 1482）。差額剛好等於同一局 log 的 `Starlight Bonus 60`（這隊沒買 Grace，60 全沒花）。推論：觀測頁右上的 `Owned` 框已經含星光頁沒花掉的星光，不是讀取時機或 ROI 讀錯（`owned_starlight` 會驗 owned − 價格 = 剩下的，讀到的三個數字一致）。改成記錄時扣掉星光頁沒花掉的部分（`RUN["starlight_unspent"]`；Convert Starlight to Cost 開著時為 0）。這個推論未在實機驗證，需要在觀測頁對照 `Owned` 框與主畫面的持有星光。
