# 2026-10-18 防禦連線漏格與開始鍵（#145）

實機：MuMu（ADB 127.0.0.1:16384，座標以 1280x720 計），遊戲 1.117.0，一局困難鏡牢第 1–3 層（放棄、沒領獎）。每次拖曳的記錄（`exp1`–`exp8.log`）與牌子動畫的逐格分數（`*.csv`）在 [data/2026-10-18-guard-chain-145/](data/2026-10-18-guard-chain-145/)；探針腳本只留在本機；錄影與標註圖附在 PR 留言（見「媒體」）。錄影全程用 OBS；遊戲主畫面的編號與標題畫面的帳號在存檔前已遮蔽。

## 結論

- 漏的多半就是**最後一格**（12 格的漏格截圖幾乎都是第 12 格沒連上；8 格的是第 7、8 格）；模擬器視窗被蓋住或縮小時也會斷在中間，斷點之後整段都沒選上（連線只能連續）。圓盤只要選到一格就亮，所以舊的「圓盤亮了」判斷看不出來；每格都選好時圓盤上方才會掛出 `START` 牌子，按開始才有反應。
- 原因是遊戲的畫面更新率：遊戲只在畫一幀時看手指在哪一格。拖曳時遊戲每秒只畫 9–30 幀（閒置時 40–55），電腦忙、模擬器視窗被蓋住或縮小時更少；手指每 10 ms 移 10 px、各格不停（#119 的參數），在兩幀之間就越過一格；最後一格更容易漏，因為手指一到就放開，遊戲還沒畫到手指停在那裡的那一幀。幀間隔（拖曳中第 90 百分位）90 ms 以內：88 次漏 7；超過 90 ms：43 次漏 27。
- 改成每格停 0.03 秒、最後一格停 0.05 秒：90 ms 以內 90 次 0 漏；超過 90 ms 仍有 32 次漏 11。所以拖完要確認開打：沒開打而牌子不在，就點左齒輪清掉連線、用更慢的拖法（每格停 0.1 秒，再不行 0.2 秒）重拖。每格停 0.1 秒在 16 核全忙（每秒 9–12 幀）時 14/14。
- 只在最後一格多停 0.1 秒（22/22）或拖過頭 20 px（17/17）在一般負載下也沒漏，但只照顧終點；電腦忙或視窗被蓋住時中間也會斷，所以每格都停一下，再加上確認開打。
- 連線不能從斷掉的地方接著拖（從最後一格往後拖會把那格換成上排技能）；從左齒輪再拖一次會清掉整條，點左齒輪也會清掉。

## 量法

- 同一回合反覆試：先按兩次勝率清掉（確認牌子不在、圓盤暗），拖一次，之後 2 秒內每張截圖找牌子。牌子出現 = 每格都選好（實際按開始的回合也一樣：牌子在就開打，不在就不開打）。
- 牌子：`Battle/BattleStart.png`（只取牌子裡的字），在圓盤上方 95x45 的範圍找，門檻 0.5。
- 遊戲畫面更新率：`dumpsys SurfaceFlinger --latency` 取遊戲圖層，每次拖曳前清掉、拖完讀，算拖曳期間的每秒幀數與幀間隔。裝置收到的觸控：`getevent -lt`，move 間隔 10.5–11 ms，跟送出的一樣，沒有被合併或延遲。

### 以前開始沒反應的損失（#145 的約 45 秒）

整合實測（2026-10-18 14:31–14:37）三次，每次：按開始 → `until` 等 3 秒 → 交回 `MirrorHub` → 重看（`still` 約 1 秒、讀回合數）→ 再按、再等 3 秒，共 3 次 → 判卡住（回合數沒變）→ L1 恢復（約 4 秒）→ 重做防禦（點頭像、拖曳；從左齒輪拖會**清掉**還在的半條連線，圓盤不亮，再等 1.5 秒）→ 改按勝率 → 開打。從第一次按開始到開打 23.4 秒（另兩次從防禦開始算 22.8、26.5 秒）；兩次就約 45 秒。
