# 04 設定結構

本章定義使用者設定：設定檔放在哪裡、怎麼寫入與檢查，以及每一組設定的欄位，包括執行選項（鏡牢任務與每個任務都用到的）、日常的任務選項、出戰順序方案、星光方案、主題包方案、飾品清單、隊伍、事件覆寫、試煉分數覆寫，以及任務清單、模擬器與排程；最後是 Agent 與 GUI 寫的其他檔案（`runs.jsonl` 等）。遊戲資料（主題包清單與預設方案、事件覆寫表、試煉表、選路權重）見 [05-game-data.md](05-game-data.md)。

## 1. 總則

- 隊伍、方案、飾品清單與覆寫表放在一份設定檔 `<root>/config/settings.json`，由自製設定 GUI（`gui/`，Tauri 2 + React/TypeScript）寫入，Agent 讀取。理由見 [ADR 0006](../adr/0006-settings-gui-writes-one-settings-file.md)。（#19，2026-10-14 定案）唯一的例外是隊伍佇列：Agent 在 bot 領到獎勵後把那一隊移到 `team_queue` 最後，鏡牢任務有起頭隊伍時在第一局新局前把它移到第一，只改佇列（第 9 節「輪替」，[ADR 0011](../adr/0011-team-list-order-is-the-queue.md)、[ADR 0014](../adr/0014-team-queue-apart-from-team-list.md)）。
- 每個任務怎麼跑的單一的值（難度、目標層數、局數上限……）是**任務選項**，每個任務都用到的 4 個是**全域選項**，都在設定檔的 `run`、`luxcavation`、`charge_enkephalin`（第 5、12 節）。任務清單、模擬器與排程也在設定檔（第 14 節）。設定視窗自己執行任務：它啟動執行器，執行器啟動 Agent、照任務清單送出任務，Agent 在任務開始時讀設定檔（[ADR 0015](../adr/0015-settings-window-runs-the-tasks.md)）。v1.0.0 的任務選項在 MXU／MFAAvalonia（[ADR 0013](../adr/0013-run-and-daily-options-in-pi-task-options.md)，已被取代）。（#6、#19，2026-10-14 定案；#811、#813，2026-11-17）
- 第一階段（A1）的 GUI 只編輯設定，不執行 bot；第二階段（A2）起 GUI 也負責執行（#811，[ADR 0015](../adr/0015-settings-window-runs-the-tasks.md)）。設定檔版本 23 只加回與新增段落，原有的段落不變。（#19，2026-10-14 定案）
- 方案與隊伍數量不限，名稱由使用者自取。方案與隊伍各有一個 id，由 GUI 產生，不隨改名或排序改變；所有引用都用 id。（#19，2026-10-14 定案）
- `<root>` 是 Agent 的根目錄，用 Agent 程式的 `__file__` 定位，不依賴工作目錄（v1.0.0 的 MFAAvalonia 在獨立資料目錄模式下工作目錄不同）。（#6）
- 設定 GUI 和 Agent 放在同一個發佈目錄，GUI 用自己執行檔所在的位置找到 `<root>`，不讓使用者選。（#19，2026-10-14 定案）
- 困難或普通、每週獎勵怎麼用這類策略是鏡牢的任務選項（第 5 節），存在設定檔。Agent 沒有狀態檔。（#8、#501，[ADR 0003](../adr/0003-screen-is-truth-state-file-only-rotation-cursor.md)）

## 2. 寫入與檢查

- 設定檔的格式由一份 JSON Schema `settings.schema.json` 描述，GUI 與 Agent 共用同一份。檔案位置在實作時決定。（#19，2026-10-14 定案）
- 設定檔有 `version` 欄位。格式改變時遞增版本，並提供遷移：GUI 讀到舊版本時遷移後寫回；Agent 讀到舊版本時在記憶體裡遷移，不寫回（移動隊伍佇列時也照舊版本寫回，只改順序）；讀到比自己新的版本就報錯。（#19）
- 最舊只讀版本 20，也就是第一個發布版 v0.1.0 出貨時的版本。版本 1–19 只有發布前的開發用設定檔，它們的遷移 2026-11-13 刪掉了（#653）；下面的版本紀錄只說明各欄位的由來，裡面寫的遷移、記錄行與狀態列提示都已經不存在。讀到比 20 舊的檔，Agent 停下、GUI 顯示讀取失敗，兩邊的原因是同一句：`settings version <n> is too old: maalc reads version 20 and later; start a new settings file in the settings GUI`。之後的版本照上一條提供遷移，從版本 20 起每一版一個。（#653）

- 視窗開在「執行」分頁：開始執行是視窗的主要動作（#815）。
- 排序清單（任務清單、隊伍清單、隊伍佇列、三種方案清單、獎勵卡順序、觀測飾品清單，以及技能替換的罪人列）整列拖曳，沒有拖曳把手，也沒有 ↑↓ 按鈕；游標是抓取的手形，拖曳中被拖的列變淡，落點畫一條線。每一列都能用 Tab 移到：Alt＋↑／↓ 移一格，Alt＋Home／End 移到最前或最後，焦點跟著那一列，螢幕閱讀器念「移到第 n 位，共 m 位」（`aria-live`，不用 `role="status"`，免得和清單下方的復原提示撞在一起）。清單有名稱（`aria-label`），列的說明（`aria-describedby`）寫移動方式。會選取的清單（任務、隊伍、方案）照舊用 Enter／Space 選取。執行中鎖住的清單不能拖、也不能用鍵盤移動，列照樣能選取。飾品清單的購買順序和主題包方案的分隔線是另一種設計，不在此列。（#873）

## 5. 執行選項（`run`）

讀法：

- 每個任務的入口動作（`TaskStart`，以及繼承它的 `LuxStart`、`ChargeStart`）在點任何東西之前讀一次設定檔：4 個全域的鍵，鏡牢任務再加其餘的鍵，日常任務加自己那一段（第 12 節）。之後所有讀這些值的地方都從那裡拿（`agent/task_options.py`），任務跑到一半存檔也不影響這次任務。任務開始時記一行 `options: ...`，列出讀到的值，webhook 只寫 `(set)`／`(not set)`。（#777、#813）
- 值不對（型別、範圍、少了鍵）是設定檔錯誤，和其他設定一樣（第 2 節）：鏡牢任務由 `PlanRun` 失敗結束，經驗本、紐本與狂氣換腦啡肽走停止程序，沒有自己選項的任務照預設跑（不送 webhook）。
- 起頭隊伍：鏡牢任務開始時，`start_team` 不在 `teams` 裡（隊伍已刪除），或那支隊伍停用，就在點任何東西之前走停止程序（有設定就送 webhook），記一行 `stop: Invalid task options:`，訊息：`run/start_team: team '<id>' was deleted in the settings GUI; pick another team, or 「照隊伍佇列」 (follow the team queue), in the options of the MirrorDungeon task in the settings GUI's task list`，停用時是 `run/start_team: team '<隊名>' (id '<id>') is disabled; enable it in the settings GUI, or pick another team, ...`。設定檔照樣讀得了：這是任務的檢查，不是設定檔的。（#805、#813）
- 目標層數大於 5 時（第 6 層起要求這一局每一層都是困難）：難度不能是 `normal`，每一支啟用的隊伍（輪替只用啟用的隊伍）的 `hard_from_floor` 必須是 1（關閉也不行），`usage` 不能是 `normal_only`。鏡牢任務開始時對設定檔的隊伍檢查，不符就在點任何東西之前失敗，訊息指出設定（`run/difficulty`、`teams/<i>/usage`、`teams/<i>/hard_from_floor`），例如 `teams/1/hard_from_floor: team 'Team b' starts HARD at floor 3, but run/target_floor 15 needs the whole run HARD (hard_from_floor 1)`；每局開始前 `PlanRun` 再對當下的隊伍檢查一次，存檔可能改了它們。GUI 存檔時不檢查；隊伍頁在用途旁放一行固定說明。（#385、#777、#813）
- 這兩條的案例是 `tests/settings_cases.json` 的 `task_start`，Agent 在任務開始時跑（`tests/test_task_options.py`）。

規則：

- 自動難度：開局前讀入口頁的 Weekly Bonuses，還有剩就跑困難，用完改普通。`target_floor` 大於 5 時一律跑困難，不看每週獎勵（`run_start.run_difficulty`；使用者 2026-11-08 定案：整局困難，不改打普通）。（#9、#385）
- 「限制局數」只算這個任務開始後領到獎勵的局數，放棄獎勵的局不算；不存檔。（#8、#30，[ADR 0003](../adr/0003-screen-is-truth-state-file-only-rotation-cursor.md)）連續 3 局放棄獎勵就停止任務（[03-decisions.md](03-decisions.md#9-全滅與陣亡) 第 9 節）。（#560）
- 「每週獎勵用完就停」的剩餘次數直接從畫面讀。（#8）
- 每週獎勵用法的說明寫「普通局的每週獎勵報酬很少，建議只用在困難」。（#30，2026-10-16 定案）
- 每週獎勵的剩餘次數從結算視窗讀。已通過第 5 層（`claim_ok`，結算視窗的 `Floor` 後面可到 15）就 Claim，沒過第 5 層放棄獎勵；只有通過層數到達 `target_floor` 的局（`target_reached`）才依用法與用量切開關。只要有一層是困難，這一局就算困難局。規則的全文只在 [03-decisions.md](03-decisions.md) 第 14 節。（#9、#17、#19、#384、#385）
- 全滅重打的計數以每場遭遇戰為單位，打贏就歸零。只有重打次數用完、而「重打用完後」為「放棄這局」時，才按 `Accept results` 回到地圖，再從設定面板按 Forfeit 結束這局，然後結算（[03-decisions.md](03-decisions.md#9-全滅與陣亡) 第 9 節）。停止時保存證據。（#16、#19）
- webhook 在停止時由 Agent 以 JSON POST 送出這局的摘要與證據存放路徑。（#14、#19）

每個方案決定開局星光的購買計畫。數量不限。（#9，#19，2026-10-14 定案）

| 欄位 | 鍵 | 類型 | 值 | 預設 | 來源 |

| 各加成的等級 | `levels` | 陣列，10 項 | 第 i 項是加成 i 的等級：`none` 不買／`base` 基礎／`plus` +／`plus2` ++ | 全部 `none` | #9、#19 |
| 購買順序 | `priority` | 陣列，10 項，不重複 | 加成編號 1–10，排在前面的先買；GUI 依點選卡片的順序排列 | 1, 2, …, 10 | #9、#19 |
| 剩下的星光換成 Cost | `convert_leftover` | 布林 | 開／關 | 關（沒用掉的星光加進結算獎勵） | #9、#19 |

- 隊伍的「自訂」星光用同一組 `levels`、`priority`、`convert_leftover`。（#19）
- GUI 仿遊戲星光頁畫成 5×2 張卡片，每張卡四種狀態對應 `levels`：未選擇 `none`、已選 `base`、`+` `plus`、`++` `plus2`。（#52）
  - 點卡片本身：未選擇 → 已選（基礎）；已選（任何等級）→ 未選擇。
  - 點 `+`／`++`：選取並設成該等級；再點亮著的那顆回到基礎。和遊戲不同，未選擇的卡不保留等級。
  - 剛選取的卡排到已選的卡後面，取消選取的卡移到最後，所以購買順序就是點選的順序；卡片左上顯示它在已選卡片中的順位。
  - 右側的 `Select All Graces` 把未選擇的卡依編號選成基礎，全部已選時改為全部取消；`Enhance All` 的 `+`／`++` 把全部卡設成該等級，全部已是該等級時改回基礎。再點一次會還原的按鈕是亮的（`aria-pressed`）：全部已選時的 `Select All Graces`、全部已是該等級時的 `+`／`++`。
  - 卡片右上顯示目前等級的價格（未選擇時顯示基礎價格），右側顯示合計。
  - 上方那一列（`Select All Graces`、`Enhance All` 的 `+`／`++`、合計、剩下的星光換成 Cost）在頁面往下捲時固定在可見範圍最上方，用自己的面板蓋住捲到下面的卡片；隊伍頁裡停在「跳到」那一列正下方，兩列不重疊（#740）。鍵盤焦點往上移到被這一列蓋住的卡片按鈕時，頁面捲到按鈕露在這一列下方。
  - 卡片的樣子照遊戲的四種狀態（#719）：未選擇是深灰藍卡面、暗框；已選（任何等級）卡面變飽和的藍、外框發藍光；`+`／`++` 時那顆按鈕變亮（鋼藍底、橘色符號），標題後面加 `+` 或 `++`，效果文字換成該等級的內容。黃字照遊戲自己的標法（#733）：效果文字的句型（`DungeonStartBuffs_MD7.json`）用 `<color=#f8c200>` 標出 `+`／`++` 改了什麼，`tools/llc_text.py` 把它帶進 `assets/resource/base/data/graces.json`，每行存成一段段文字，黃的那段 `up` 為真，GUI 照資料標（`gui/src/graceText.ts`），不自己比對。客戶端的英文句型（`EN_DungeonStartBuffs_MD7.json`）用同樣的標籤標同樣的地方，英文卡片照它標（#751）。所以「選擇獲得2件」整段是黃字，「(最多+9)」只有「9」是黃字，和遊戲一樣。顏色標籤可以巢狀，內層的顏色到它自己的結束標籤為止（TextMeshPro 的顏色堆疊）；句型裡的另一種顏色 `#627eff` 是遊戲的藍色關鍵詞，GUI 不顯示；出現這兩種以外的顏色時工具直接報錯。基礎等級的句型沒有黃字。標題左邊是遊戲的恩惠圖示（`assets/resource/base/data/grace_icons/`，`tools/grace_icons.py` 從遊戲資料取出）。
  - 卡面、選取後發光的卡面、游標移上去的外框、`+`／`++` 的底板（亮與不亮）和 `+` 符號、價格與合計的星光圖示、`Enhance All` 面板和整頁背景都是遊戲自己的圖（#726）：`tools/grace_icons.py` 從 APK 玩家資料依星光頁 prefab 用到的精靈圖取出，寫到 `assets/resource/base/data/grace_card/`（10 個檔，共約 95 KB）。卡片照卡面的像素排版：價格在卡面的價格條上，圖示在卡面的框格裡，標題在標題帶。卡面的頂端與底部保持原比例，中段隨文字拉長，和遊戲一樣（遊戲把 380 × 438 的卡面畫成 450 × 569）。卡片至少 216 px 寬，標題字級隨卡寬（寬度的 6.8 %，13–19 px），所以中文標題（最長「傾落的流星雨++」）不折行；預設視窗 1500 px 寬（#732），隊伍頁和星光方案頁一列 5 張（每張 216–222 px），1280 px 一列 4 張，800 px 一列 2 張。標題一律排成一行，放不下時縮小字級，像遊戲那樣（#751）：GUI 量出標題排成一行的寬度，算出剛好放進標題帶的字級，最小 12 px，比這更小才折行。英文標題用窄體 Barlow Condensed（遊戲的英文標題也是窄體）；最長的「Cumulating Starcloud++」在最窄的卡（216 px）縮到 13 px，所以這些卡寬下沒有標題折行，中文標題也不用縮。遊戲檔沒有的部分照舊是 CSS：購買順位的金色牌（bot 自己的資訊）、焦點框、`.starlight` 的外框、游標移到 `+`／`++` 與 `Select All Graces` 上時的提亮（遊戲的 Hover 圖和亮起的底板是同一張，拿來當 hover 會和亮起分不出來）。
- 加成依遊戲星光頁的順序編號，標籤用遊戲的英文名稱。（#9、#18）

| 編號 | 加成（英文名稱） | 基礎價格（星光） |
|---|---|---|
| 1 | `Star of the Beginning` | 10 |
| 2 | `Cumulating Starcloud` | 10 |
| 3 | `Interstellar Travel` | 20 |
| 4 | `Star-shower` | 20 |
| 5 | `Binary Star-shop` | 30 |
| 6 | `Moon Star-shop` | 30 |

- 編號依星光頁上排左到右、再下排左到右。名稱與基礎價格是 Mirror of Names and Spiders 這一季的實機畫面（實機：captures/03_starlight_page.png）。
- 「基礎」是卡片本身的效果，價格標在卡片右上；「+」「++」對應卡片底部的 `+`、`++` 兩個按鈕。（實機：captures/03_starlight_page.png）
- 點法與價格（2026-10-14 實機，Limbus 1.116.2，這個帳號 10 張卡都能用 `+`、`++`）：
  - 點卡片本身就是選取或取消選取這張卡，選取時卡片整張變白。
  - `+`、`++` 只設定這張卡的等級，不會選取它；再點亮著的那顆按鈕會回到基礎等級。卡片右上的價格跟著變成這個等級的總價。
  - 各等級的總價是基礎價格的 1／2／3 倍，10 張卡都一樣（例如 `Star of the Beginning` 10／20／30、`Perfected Possibility` 60／120／180）。
  - 選取時花的是卡片右上當下的價格，`Available` 立刻扣掉；改已選卡片的等級也會立刻反映差額。
  - 遊戲不擋買不起的卡：選了超過 `Available` 的卡，差額會從持有的星光扣，畫面變成 `Owned 4035-60`、`Available 0+60`（取消選取後恢復）。設定了的加成可以花持有的星光（#96）；所以買不起（`Available` 加 `Owned` 都不夠）要由 Agent 先用價格算好，點完再讀 `Available` 確認扣的和價格一致（出現 `+N` 表示 N 由持有的星光付）。
  - 連續點太快（間隔不到約 1 秒）會漏掉輸入。離開再回到星光頁時，選取與等級都重設。
- 可用的星光是星光頁右上的 `Available`，等於選隊頁該隊的 `Starlight Bonus`，不是持有的 `Owned`。「剩下的星光換成 Cost」對應星光確認對話框的 `Convert Starlight to Cost`；不換時，剩下的星光加進這局的結算獎勵。（實機：captures/01_team_picker.png、captures/04_starlight_confirm.png）
- 依購買順序購買。（#9、#19）
- 買不起（`Available` 加 `Owned` 仍不夠）時依鏡牢任務選項「星光買不起時」處理：`skip` 跳過這張繼續買下一張，`stop` 停止整個任務：方案裡只要有一張買不起，就一張都不買，這局停在星光頁。買不起的加成不降級購買。（#9、#25）

- 方案裡沒列出的主題包用 `unlisted` 的分數，例如新一季才出現的主題包；GUI 把這些包和「沒列出的包」放在同一欄，拖動「沒列出的包」就是改 `unlisted`。空的方案等於全部用 `unlisted`，不報錯。（#11、#19，2026-10-14 定案；#240）
- 隊伍只能選「預設」或使用者的方案，沒有隊伍專屬的自訂主題包標記。（#19，2026-10-14 定案）

規則：

- 出戰順序與星光可以引用方案，也可以選「自訂」，直接填只給這支隊伍用的值。把自訂的值存成方案、或從方案複製成自訂，由 GUI 提供。（#19，2026-10-14 定案）
- 「困難局從第 N 層起轉困難」只在這一局是困難局時有效。關閉時這隊打普通；只有鏡牢任務選項的難度明確設成「困難」時以任務選項為準，整局每層都困難。難度是「自動」時，就算還有每週獎勵，輪到這隊的局也是普通局（`run_start.team_difficulty`；#137，2026-10-18 定案）。第 N 層之前用普通。任何一層選了困難後，之後都不能切回普通。普通局第 N 層（N > 1）能不能切到困難還沒實測；不能的話這個欄位會移除（[03-decisions.md](03-decisions.md#未決)）。（#9、#19）
- 獎勵卡比對不到任何類型時選第一張。（#11）

### 輪替

- `team_queue` 就是隊伍佇列：`teams` 每個 id 各一次，順序就是輪到的先後。`teams` 的順序只是隊伍清單的顯示順序，選隊不看它。每一局由佇列裡第一支啟用、用途符合這局難度的隊伍出戰；用途不符或停用的隊伍跳過，留在原位。沒有任何可用的隊伍就以成功結束任務。（#9、#19、#364、#501、#803，[ADR 0014](../adr/0014-team-queue-apart-from-team-list.md)）
- bot 看到某隊完成一局並領到獎勵後，Agent 重新讀設定檔，把那一隊移到 `team_queue` 最後再寫回，`teams` 的順序與其他內容不動；放棄、停止，以及推不回隊伍的接續局都不動。啟用的隊伍因此依序各跑一局、循環下去。磁碟上的檔還是版本 20、21 時（GUI 還沒寫回），它的佇列就是 `teams` 的順序：Agent 在 `teams` 裡移動，照原本的版本寫回（第 2 節）。（#501、#803，[ADR 0011](../adr/0011-team-list-order-is-the-queue.md)）
- 鏡牢任務的起頭隊伍（`run.start_team`，第 5 節）：任務要開第一局新局時，入口頁的 `PlanRun` 把它當成佇列第一來選隊；這一局確定要開（腦啡肽模組的檢查通過、按 Enter 之前），Agent 才把它移到 `team_queue` 第一，寫法和領獎後相同（版本 20、21 的檔在 `teams` 裡移動），記一行 `team queue: start team '<隊名>' (run.start_team) to the head`，本來就在第一時是 `... is already at the head`。沒開局就結束任務（沒事可做，例如每週獎勵用完就停），或先回 Drive 頁讀腦啡肽模組的那一趟，檔案不動。移到第一等於把排在它前面的隊伍依序移到最後，所以 GUI 的合併照下面的做法就對。任務開始時已經有一局在跑（Agent 重開、接續暫停的局、領上一局的獎勵）：那一局照移動前的佇列推回隊伍，起頭隊伍等這個任務的第一局新局才排。起頭隊伍的用途不符合這一局的難度：照常往後找第一支符合的隊伍，記一行 `start team '<隊名>' (run.start_team) is <usage>: a <難度> run passes over it, and it keeps its place in the team queue`，它留在佇列第一。只排一次：之後的局照佇列輪替。設定檔會記住選擇，所以每次開始這個任務都會再排一次。（#805，[ADR 0014](../adr/0014-team-queue-apart-from-team-list.md)）
- 隊伍清單的排序（拖曳或 Alt＋方向鍵）只改 `teams` 的順序，清單不標順位；佇列只在「執行」分頁鏡牢選項的「隊伍佇列」顯示與調整，因為只有鏡牢讀它。隊伍清單下方一行：「清單順序只是顯示用。哪一支先出戰，在「執行」分頁點鏡牢，用「隊伍佇列」排。新增的隊伍排在最後。」（#804、#878）新增的隊伍加在 `teams` 與 `team_queue` 的最後；刪除的隊伍從兩者移除，復原時兩邊都回到原位。（#803）
- 「隊伍佇列（每局輪替）」是「執行」分頁鏡牢任務選項最上面的框，佔框的全寬，下面是「每一局」「每週獎勵」「出錯時」。它照 `team_queue` 列出每支隊伍，每一列共用同一組欄：順位、名稱（放不下截短加「…」）、遊戲內欄位（TEAMS #N，等寬數字）、用途（只標「只跑困難」「只跑普通」）、下一局、旗子，列的右緣等於框的右緣。停用的隊伍淡色加刪除線、留在原位，螢幕閱讀器念「（停用）」，列的滑鼠提示「停用：輪到它時跳過」；隊伍清單用同一種樣式。拖曳與 Alt＋方向鍵只改 `team_queue`。Agent 改了佇列，設定視窗下一次讀檔後照新順序顯示（下一條的合併）。`team_queue` 裡不是任何隊伍的 id 自成一列、標紅，點這個問題會跳到「執行」分頁、選取鏡牢、焦點在那一列。怎麼輪替（領到獎勵的隊伍移到最後；旗子只排任務的第一局新局）是佇列的滑鼠提示。（#804、#878）
- 「下一局」：困難的下一局是佇列裡第一支啟用、用途可跑困難的隊伍，普通也一樣；有起頭隊伍時從它算起（Agent 的 `headed`）；難度設成只打一種時只算那一種。兩個難度是不同隊伍時（包括只有一個難度有隊伍），各自的列寫琥珀色的「下一局」加難度牌（小框寫「普通」或「困難」，困難有底色、普通只有外框）；同一隊或只打一種時只寫「下一局」。`tests/settings_cases.json` 的 `next_run` 讓 Agent 和設定視窗算出同樣的隊伍。任務清單的鏡牢列第二行也寫「下一局」：普通在前，各接難度牌和隊名（一隊時只寫隊名），起頭隊伍是一支啟用的隊伍時後面多一面亮起的旗子；只在第一個勾選的鏡牢列，限一行，放不下就整行拿掉（同時 `aria-hidden`），執行中鏡牢任務開始跑以後收起，執行結束後再出現。（#878）
- 旗子（起頭隊伍，`run.start_team`）：每一列最右邊一個 16 px 的旗子圖示，平常淡淡顯示，指定的那支填滿、琥珀色；按一下指定「這次從這支開始」，再按一次取消，只能指定一支，停用的隊伍不能按（旗子已亮在停用的隊伍上時，可以按來取消）。滑鼠停留或鍵盤焦點在旗子上時，上方浮出「這次從這支開始」（亮著時「這次從這支開始（再按取消）」）。螢幕閱讀器念「這次從<隊名>開始」，亮著時念「取消「這次從<隊名>開始」」（`aria-pressed`）。旗子亮著時佇列下方一行「旗子會存進設定檔，每次開始都會再排一次，用完記得改回。」；起頭隊伍停用或已刪除時改成一行警示，說任務一開始就停下（已刪除的隊伍沒有那一列，警示旁有「取消旗子」按鈕）。執行中佇列鎖住：不能拖、旗子全部停用、每一列淡化到 0.45。（#805、#878）
- GUI 開著時 Agent 改了設定檔：GUI 每 2 秒、視窗回到前景與存檔前都重新讀檔；沒有未儲存的修改就直接採用新的檔案，有的話保留修改，再把 Agent 移到 `team_queue` 最後的隊伍也移到修改後佇列的最後，所以存檔不會蓋掉 Agent 寫的佇列，使用者還沒存的清單排序也留著。檔案被刪掉時保留編輯內容，存檔時重新寫入；開啟時沒有檔案、之後才出現的，以新設定檔為基準合併。GUI 與 Agent 寫入前都先確認檔案仍是自己上次讀到的內容，不是就重新讀檔再合併（[ADR 0011](../adr/0011-team-list-order-is-the-queue.md)）。狀態列顯示「設定檔在外部被改過，已重新讀取」或「設定檔不見了，儲存時會重新寫入」；存檔重試 3 次仍被拒（檔案一直被改動，或讀不懂），顯示「沒有儲存：設定檔一直在外部被改動，或讀不懂」，什麼都不寫。編輯中的隊伍在清單裡被移走時（GUI 還沒寫回的版本 20、21 檔，Agent 移的是 `teams`），右邊仍顯示同一隊。（#501、#803）
- 沒有任何啟用的隊伍不是設定檔的錯誤：只跑日常的人不必設隊伍。鏡牢任務開局時才檢查，沒有就以成功結束任務（回主畫面、記一筆 `no enabled team`，和「沒有可用的隊伍」同一條路，spec 06、#362），不報錯。（#364）
- 舊版的輪替游標（#501 之前，存在 `<root>/state/<控制器位址>.json`）在鏡牢任務開始時遷移一次：佇列轉到游標那一隊排第一，然後刪掉所有狀態檔。游標指著停用或已刪除的隊伍時不轉。設定檔讀不到時狀態檔留到下次。（#501）
- 選隊頁顯示的隊伍和佇列選出的不同時，以畫面為準。（#8，[ADR 0003](../adr/0003-screen-is-truth-state-file-only-rotation-cursor.md)）

## 12. 日常的任務選項（`luxcavation`、`charge_enkephalin`）

經驗本（任務 `ExpLuxcavation`，`luxcavation.exp`）、紐本（`ThreadLuxcavation`，`luxcavation.thread`，#368）與狂氣換腦啡肽（`ChargeEnkephalin`，`charge_enkephalin`，#373）怎麼跑，鍵名與預設值照版本 20（#813，[ADR 0015](../adr/0015-settings-window-runs-the-tasks.md)）。讀法同第 5 節：入口動作（`LuxStart`、`ChargeStart`）在點任何東西之前讀一次，記一行 `options: ...`。要跑哪些日常、依什麼順序，由任務清單決定（第 14 節，[ADR 0010](../adr/0010-one-pi-task-per-daily.md)）。設定視窗的「執行」分頁在任務清單點那個任務，右邊顯示它的選項；隊伍的下拉選單直接列出設定檔裡的隊伍，新增或改名立刻看得到，選的隊伍已經刪掉時顯示「已刪除的隊伍」與任務會停下的說明（#814）。（#362、#366）

## 14. 任務清單、模擬器與排程（`tasks`、`emulator`、`schedules`）

設定視窗的「執行」分頁與執行器用這三段（#811）。「執行」分頁編輯任務清單、模擬器與排程（#814、#815、#816），按「開始」或時間到時照它們執行（#815、#816）。Agent 不讀它們。

「執行」分頁（#814，版面 #875）：兩欄，頁面不放標題，三個區塊的第一個框頂端在同一條線，兩道欄間距 20 px。左欄是任務清單，旁邊是點選的任務的選項（第 5、12 節）：鏡牢的選項分成幾個各有標題的框，其他任務的選項放在一個框裡，框標題寫任務名稱、不寫 id；下面是全域選項（預設摺疊的面板）與定時執行。右欄是執行台，由上到下：開始、停止與狀態列，模擬器，即時記錄；閒置與執行中順序相同。執行台高度是視窗高度減標頭、分頁列與上下邊距，記錄框填滿剩下的高度，所以執行台不自己捲動，按下開始時版面不動；捲動頁面時執行台與任務清單固定在同一個頂端位置。頁面的 DOM 順序把執行台排在最前，第一下 Tab 就到「開始」。頁面保留捲軸的位置（`scrollbar-gutter: stable`），切換任務時欄位不左右跳。視窗寬度 1180 px 以下時排成一欄：開始、停止與狀態列一行固定在頁面頂端（下面一條細線），接著是任務清單與選項，然後是模擬器與即時記錄；記錄在開始執行前是摺疊的面板，「顯示 MaaFramework 的原生輸出」開關在它的標題那一行（點開關只勾選，點標題的字才收合）。每個欄位的設定鍵（例如 `run/start_team`、`luxcavation/exp/team`，和 Agent 停止訊息裡的寫法一樣）在滑鼠移到那個欄位上（包括它的標籤）、或那個欄位畫出焦點框時（用鍵盤把焦點移進去；文字框與數字框有焦點時都算，用滑鼠點開關或下拉選單則不算），以小字顯示在標籤後面；沒顯示時也佔著它的位置，所以顯示時版面不動。標籤與設定鍵放不下一行時設定鍵截短，標籤永遠一行，滑鼠停在設定鍵上看得到完整的鍵。螢幕閱讀器把標籤念成欄位的名稱，設定鍵當作欄位的說明念，不論有沒有顯示。分頁和其他分頁一樣在存檔時才寫入設定檔。

**執行**（#815；執行器是 `runner/`，協定在 `runner/protocol.py`，兩邊的共用案例是 `tests/runner_cases.json`，視窗這邊是 `gui/src-tauri/src/runner.rs`）：

- **開始**：開始與停止直接放在頁面上，沒有框；開始鈕高度等於任務列高度，執行中停用時不是琥珀色。「按「開始」先儲存設定…」是開始鈕的滑鼠提示。有未儲存的變更時先存檔（每個任務開始時讀設定檔），存檔中狀態列寫「儲存中…」，存檔被擋下就不開始。之後視窗用 `python/`（開發用的安裝：`interface.json` 的 `child_exec`）跑 `runner/__main__.py`，把它放進 Windows Job Object，送出勾選的任務（id 就是入口節點，照清單順序）與 `emulator` 三個值。沒有勾選任務或設定有問題時「開始」不能按，並寫原因。位址上沒有裝置、而實例編號與 MuMuManager 路徑都有時，執行器用 MuMuManager 啟動那個實例，每秒看一次：偵測列出那個位址，而且那個位址的 adb 回 `device` 後，再等 5 秒才連線（#831：MuMuManager 開機約 2 秒就列出實例，adb 要再十多秒才不是 `offline`；MaaFramework 連線時選定這次執行的截圖方式，所以等系統開好再連）。連線失敗時每秒重試。這些都在啟動後 120 秒內，逾時就是 `device_timeout`，訊息寫 adb 最後怎麼回；在第 120 秒才回 `device` 的，照樣等 5 秒、連一次。
- **停止**：視窗送停止命令；執行器回報停不下來（`error stop_timeout`），或停止命令送出 75 秒後還沒結束（執行器自己等 60 秒），視窗就結束整個程序樹（執行器、bot、它開的 adb server）。執行器結束時，它留下還在跑的程式（例如它開的 adb server）也一起結束；下次連線時 adb server 會再啟動。
- **狀態**：閒置時狀態列不寫字（給螢幕閱讀器的 live region 留著）。開始跑任務前寫連線（啟動 MuMu、等待模擬器、連線中、已連線與位址）與資源載入；開始跑任務後寫「第幾個／共幾個」（執行中的是第幾個；沒有執行中的時寫結束了幾個）；跑完寫結果。後面接「 · 已跑多久」（`mm:ss`，一小時起 `h:mm:ss`），從這次執行的第一行記錄算起，每秒更新，結束後停在跑了多久；計時在 `role="status"` 之外，螢幕閱讀器不會每秒念。各任務的狀態寫在任務清單的列上（#877，見下面「任務清單」）：等待、執行中、成功、失敗、已停止、已取消之一。失敗或被取消的任務附原因：執行器送的原因；執行器沒送時（任務自己失敗的停止，執行器只在 bot 停下整條清單時送原因），用 bot 在這個任務開始後（`[maalc] task <id> started`）最後一行 `[maalc] stop: <原因>`，bot 第 n 次開始某個任務就是這次執行的第 n 項那個任務，所以前一個任務的停止行不會變成下一個任務的原因。bot 自己停下整條清單（帳號層級的停止）時，當時正在跑的任務標失敗並附同一個原因，MaaFramework 回報它成功也一樣（#870）。按停止時正在跑的任務標已停止，MaaFramework 回報它成功也一樣（agent 的動作在 `post_stop` 後正常返回時，它回報成功，#832）；執行器取到停止命令前已經跑完的任務照它的結果標。
- **即時記錄**：執行器的 `log` 事件（`[run]` 行、bot 的 `[maalc]` 行），以及不合協定的輸出與 stderr 行；MaaFramework 的原生輸出（`console`）預設不顯示，勾選標題那一行的「顯示 MaaFramework 的原生輸出」才顯示（「例如點擊座標」是開關的滑鼠提示）。空著時沒有底色，只寫一行淡色的「還沒有記錄」。失敗或停止的行用失敗的顏色：`status=failed`、`status=stopped`、`[run] error`、`[run] end failed`、`[run] end stopped`、`[maalc] stop:`。執行器與 bot 的行裡的任務 id 與 bot 的英文任務名（`EXP Luxcavation`、`Thread Luxcavation`）顯示成清單上的名稱，滑鼠停在那一行看到原文；`logs/runner/` 的記錄檔照原文寫。視窗只留最近 2000 行，每次執行的完整記錄在 `logs/runner/`（這兩句是「即時記錄」標題的滑鼠提示）。新的一次執行清空視窗的記錄。重新載入頁面（F5）時，頁面從後端拿回這次執行到目前的訊息（記錄最多 2000 行）。
- **執行器意外結束**（結束時沒送 `end`）：寫明結束碼與最後 20 行輸出，不自己重跑，狀態列寫這次執行失敗；是視窗結束程序樹的，改寫視窗為什麼結束它，狀態列寫已停止。這次執行算失敗：執行中的任務標失敗（按過停止時標已停止），還沒輪到的標已取消。
- **執行中**：任務清單（勾選、拖曳、Alt＋方向鍵、複製、移除、加入）、任務選項、全域選項與模擬器（下拉選單、偵測、欄位）都不能改；「加入任務」的位置換成一行淡色、沒有框的「🔒 執行中，相關設定不可更改」，這是整頁唯一的鎖定說明（刪除後的「復原」也等執行結束才出現）。點任務照樣顯示它的選項；其他分頁照常能改、能存。執行中標頭不顯示「放棄變更」之後的「復原」：它會放回這次執行讀的設定。執行結束後解鎖。

**任務清單**（`tasks`）：陣列，每一項是一個任務與它的勾選，順序就是執行順序。同一個任務可以列不只一次（#811，2026-11-18 審查後補上）：例如換腦啡肽模組在副本前後各跑一次，v1 的 MXU 也允許。每一項各自勾選、排順序，所有項共用那個任務的任務選項（第 5、12 節）；執行器照順序送出每一個勾選的項目，同一個任務勾了兩項就跑兩次，兩列各寫自己的狀態。

| 欄位 | 鍵 | 類型 | 值 | 預設 |
|---|---|---|---|---|
| 任務 | `id` | 字串 | `MirrorDungeon`、`AssembleModules`、`ClaimMail`、`ExpLuxcavation`、`ThreadLuxcavation`、`ClaimPassMissions`、`ChargeEnkephalin` 之一，也是它的入口節點（`interface.json` 的 `task`，`tests/test_interface.py` 檢查兩邊一致） | — |
| 勾選 | `enabled` | 布林 | 開始時跑不跑這個任務 | 關（新檔清單的各項是開，見下） |

- 新的設定檔與遷移（版本 22 的檔沒有 `tasks`）：每個任務一項、全部勾選，裝好就能跑，照使用者的順序列 7 項（2026-11-20，#874）：`ExpLuxcavation`、`ThreadLuxcavation`、`ClaimMail`、`ChargeEnkephalin`、`AssembleModules`、`ClaimPassMissions`、`MirrorDungeon`，也就是 README 的建議順序。這份清單是 schema 裡 `tasks` 的 `default`，Agent 與 GUI 都從那裡讀（`tests/test_settings.py` 核對它和 README 的建議順序一致）。#874 改這份預設時鍵與型別都沒變，所以設定檔版本不升；已經有 `tasks` 的檔照它自己的清單。
- 列幾次、順序都不限，也可以少列（schema 不檢查）。讀檔時清單照檔案原樣：少列的任務不補回，「執行」分頁沒有它那一列，存檔後也沒有，要加回用「加入任務」（#874，取代 #814 讀檔時補在最後的做法）；Agent 本來就不補。從 v1.0.0 的 MXU 讀回時，MXU 沒列的任務補在最後、不勾（第 2 節），那是一次性的匯入。不認得的任務 id 是 schema 的錯。
- 「執行」分頁（#877）：每一項一列：勾選框、名稱，列了不只一次的任務加「#n」標籤（標籤的提示寫「第 n 項。「名稱」列了 N 項：各自勾選、排順序，選項共用右邊這一份。」）。列的滑鼠提示寫「名稱（id）」，任務 id 只出現在這裡。勾選框與名稱對第一行垂直置中，點勾選框只勾選、不改選取；勾選框決定 `enabled`，拖曳或 Alt＋方向鍵改順序。點一列在右邊顯示那個任務的選項，沒有選項的任務寫「這個任務沒有選項」。同一個任務的各項，勾選框的名稱帶它是第幾項（螢幕閱讀器念「執行第 2 項「換腦啡肽模組」」）。點的那一項記在它是那個任務的第幾項，所以拖動後選取還在同一項上。
  - 每一列的複製鈕與 ✕ 平常不顯示，游標停在列上或鍵盤焦點在列上（或那兩個按鈕上）時浮在第一行的右端，不佔位置，下面一段漸層蓋住名稱的尾巴；名稱是「在下面再加一項「名稱」」「從清單移除「名稱」」。複製在那一列正下方多一項同一個任務（不勾），並選取它。✕ 拿掉那一列，任務的最後一項也能拿掉；清單下方寫「已刪除「名稱」。」與「復原」，復原放回原來的位置並選取它。選取留在原來那一項；刪的就是選取的那一項時，移到補上它位置的那一列（刪的是最後一列時是新的最後一列）。按了 ✕ 或「復原」，焦點移到補上的那一列或放回的那一列（清單空了移到「加入任務」），不會掉回頁首。
  - 清單下方的「＋ 加入任務」打開一個浮在頁面上的選單（不推動下面），照新設定檔的任務順序（schema 預設的 `tasks`）列出每個任務，清單沒有它的寫「不在清單」，列了不只一次的寫「已列 n 項」；選了加到清單最後、不勾，並選取它。打開後焦點在第一項（有焦點的那一項有底色），↑↓／Home／End 移動，游標移到哪一項焦點就跟過去，Esc 關掉並回到按鈕，Tab 或點外面也會關。清單是空的時寫「清單是空的。按「加入任務」加一個。」
  - 執行中與執行後：執行器照清單順序送出勾選的項目，所以第 k 個勾選的列就是這次執行的第 k 個任務，各列右邊寫它的狀態。只有狀態字有顏色（執行中與已停止是琥珀色、成功青色、失敗紅色），列本身不變色、不改框、沒有動畫，不和選取的列或「設定有錯」的紅框撞在一起；這次沒跑的列（沒勾）變淡。失敗或被取消的列，名稱下面寫原因（見「狀態」），原因裡的任務名換成清單上的名稱，開頭就是那一列自己的名稱時拿掉；原因照 bot 的英文，翻成中文是 #881。執行結束後狀態留著，直到清單被改（勾選、移動、複製、移除、加入），那時清單和這次執行對不上，狀態消失，清單改回原樣（取消勾選再勾回、刪除後復原）也不再出現。重新載入頁面（F5）時：執行中取回的，以頁面那時讀到的清單當作這次執行的清單（執行中清單不能改）；已經結束的不在列上寫狀態，因為頁面不知道它開始時的清單，清單可能已經改過（開始鈕旁的狀態列與即時記錄照常顯示）。是不是還在執行照後端的回覆，不看取回訊息時的那一刻。
  - 選項有問題的任務，它的每一列都標紅，點問題會切到那個任務的第一項、聚焦那個欄位。

**模擬器**（`emulator`）：

| 欄位 | 鍵 | 類型 | 值 | 預設 |
|---|---|---|---|---|
| 位址 | `address` | 字串或 `null` | adb 位址，例如 `127.0.0.1:16384`；開始時重新偵測，再照位址挑 | `null` |
| MuMu 實例編號 | `mumu_index` | 整數 ≥ 0 或 `null` | 找不到那個位址時，用 MuMuManager 啟動這個實例 | `null` |
| MuMuManager 路徑 | `mumu_manager` | 字串或 `null` | 上次偵測找到的 `MuMuManager.exe` | `null` |

- 「執行」分頁的模擬器框（#876）：一個下拉選單，旁邊是偵測按鈕；三個值的欄位收在下面的「手動設定」，清空就是 `null`（#814、#815）。「手動設定」是預設摺疊的面板，展開三角和其他面板一樣，標題的滑鼠提示寫「adb 位址、MuMu 實例、MuMuManager 路徑」；展開後 adb 位址與 MuMu 實例編號並排、兩個輸入框頂端對齊，MuMuManager 路徑在下一行。「adb 位址」「MuMu 實例編號」怎麼用寫在它們的滑鼠提示，螢幕閱讀器接在設定鍵後面念。執行中整個框鎖住（下拉選單、偵測、三個欄位）。
- 偵測：打開「執行」分頁時自動偵測一次；執行中打開分頁不偵測（偵測按鈕那時鎖住），也不寫提示，結束後按「偵測」才偵測。執行中重新載入頁面、排程打開視窗跑任務，都算執行中打開：第一次偵測等視窗知道有沒有執行中或正要開始的執行。按「偵測」或「重新偵測」也偵測。偵測另開一個執行器做 `scan`（最多 60 秒），只列出 adb 裝置，不連線。
- 按鈕在偵測前寫「偵測」，偵測中寫「偵測中…」並停用，偵測過寫「重新偵測」。偵測中只寫在按鈕上，不在按鈕下多一行，所以偵測中與偵測完記錄框不動。
- 還沒偵測、偵測中、沒找到、偵測失敗時，下拉選單只有一項，寫目前的設定：「目前：MuMu 實例 0（127.0.0.1:16384）」，沒有實例編號時「目前：<位址>」，沒有位址時「還沒設定模擬器」。
- 找到的模擬器就是下拉選單的選項，不另寫找到幾台：MuMu 排前面（下拉選單的滑鼠提示），MuMu 寫實例編號與位址，其他寫名稱與位址。設定的三個值和選某一項會填的相同時預先選它（位址照執行器的認法，`localhost` 與 `127.0.0.1` 同一個埠算同一台），否則第一項是「目前：…・選一台…」。只有位址相同時（例如讀回 MXU 後：MXU 不存實例編號與 MuMuManager 路徑）也從「…・選一台…」開始，因為下拉選單選它目前顯示的那一項不會觸發變更，選了等於沒選（#833）。選一台就填入三個值：MuMu 的位址、實例編號與 MuMuManager 路徑，其他模擬器的位址，實例編號與路徑清成 `null`。和其他欄位一樣，存檔才寫入。
- 沒找到時下拉選單下面寫「沒偵測到開著的模擬器。」（接下來怎麼做是它的滑鼠提示），偵測失敗時寫「偵測失敗：<原因>」。螢幕閱讀器把這一行念成下拉選單的說明，沒找到時接著念接下來怎麼做。（#815、#876）

**排程**（`schedules`）：陣列，每個排程一個 Windows 工作排程器的工作（#811「定時執行」）。

| 欄位 | 鍵 | 類型 | 值 | 預設 |
|---|---|---|---|---|
| id | `id` | 字串 | GUI 產生，工作名稱與 `maalc-gui.exe --run <id>` 用它；不重複（跨物件檢查，第 2 節） | — |
| 星期 | `days` | 陣列，至少 1 項，不重複 | `mon`、`tue`、`wed`、`thu`、`fri`、`sat`、`sun` | — |
| 時間 | `time` | 字串 `HH:MM` | 本機時間，24 小時制 | — |
| 叫醒電腦 | `wake` | 布林 | 開：時間到時叫醒睡眠中的電腦 | 開 |

**定時執行**（#816，`gui/src/Schedules.tsx`、`gui/src-tauri/src/schedule.rs`）：

- 「執行」分頁的「定時執行」一區（左欄全域選項之下）：「新增排程」加一列，id 是還沒用的 `s1`、`s2`……裡最小的，每天、`05:10`（每日重置之後）、叫醒電腦開；每列有星期一到日的勾選、時間、叫醒電腦開關與刪除。最後一個勾選的星期不能取消，清空時間會留著原本的時間，所以分頁做不出 schema 擋下的排程。排程不影響這次執行，執行中照常能改、能存。
- 每個排程一個 Windows 工作排程器的工作，放在根資料夾，名稱 `maalc-<資料夾的鍵>-<id>`（鍵見第 2 節「每個 maalc 資料夾同時只開一個視窗」），兩份安裝不會互相覆蓋。工作執行 `"<root>\maalc-gui.exe" --run <id>`，工作資料夾是 `<root>`：
  - 每週的星期與時間（本機時間）各一個觸發；錯過的時段在使用者登入後補跑（`StartWhenAvailable`）；`wake` 開時叫醒電腦（`WakeToRun`，還要電源選項允許喚醒計時器）。
  - 目前使用者、一般權限（`LeastPrivilege`）、只在使用者登入時執行（`InteractiveToken`，不存密碼）：模擬器與視窗要在使用者的桌面上。
  - 用電池也開始、也不停；不設執行時間上限（`PT0S`，一次執行可能好幾個小時）；優先順序 4（一般；工作排程器預設的 7 會讓視窗、執行器與它開的模擬器都降到低於一般）；同一個工作還在跑時照樣再開一個（`Parallel`：上次排程開的視窗可能還開著，新的這次交給它）。
  - 視窗經工作排程器的 COM 介面寫入與讀回工作（`schtasks` 的輸出用主控台字碼頁，中文路徑會讀錯）。
- 視窗每次啟動（設定檔讀進來、排程通過檢查時）與每次存檔後，讓工作排程器和設定檔一致：讀回這個資料夾的每個工作，指令、參數、工作資料夾、星期、時間、叫醒、補跑、登入方式、權限與上面的設定有一項不同就重寫，缺的補上，刪掉的排程把工作也刪掉。另一個資料夾的 maalc 工作（名稱 `maalc-<8 位十六進位>-`）指的磁碟機或共用資料夾在、`maalc-gui.exe` 卻不在（那個資料夾搬走或刪了）就刪掉；還在的是另一份安裝的，不動；磁碟機或共用資料夾不在（隨身碟拔了、NAS 關了）也不動。所以資料夾搬家後打開一次視窗，工作就改成新路徑。區塊寫出結果：和設定檔一致的工作數與每列的工作名稱、寫不進去的排程與原因、連不上工作排程器的原因，排程有未儲存的變更時寫「存檔後才寫入」。開發用建置（`tauri dev`）設了 `MAALC_ROOT` 時不寫工作：工作啟動的 exe 沒有 `MAALC_ROOT`，會開錯資料夾。
- `maalc-gui.exe --run <id>`：
  - 視窗沒開：打開視窗，設定讀進來後像按「開始」一樣跑任務清單（切到「執行」分頁，捲到執行台：停止鈕與即時記錄；窄視窗捲到即時記錄，停止鈕在頁面頂端固定的那一行），跑完自動關閉。跑完時有未儲存的變更（使用者在執行中改了別的分頁），或執行器意外結束（結束碼與最後的輸出只在這個視窗裡），視窗留著並寫明。
  - 視窗已開：交給那個視窗，叫到最前面，一樣像按「開始」（切到「執行」分頁，捲到執行台，窄視窗捲到即時記錄）：有未儲存的變更先存檔，存檔被擋下就不跑。跑完視窗留著。
  - 已經在跑（或正在開始）：這次略過。同一時間的兩個排程，第一個跑，第二個略過。
  - 程式更新正在套用，或沒做完、沒能全部還原：這次排程開始的當下，`cache/update/apply.json` 是 `applying`，或是 `failed` 而沒有全部還原，而且 `cache/update/old/` 還有檔案（第 13 節，`update.rs` 的 `left_unfinished`）。這次略過，視窗留著：資料夾裡可能一半是新版的檔案，不能啟動執行器。使用者把檔案搬回、清空 `old/` 之後，下一次排程照常執行，已經開著的視窗也一樣。套用剛開始、還沒搬走第一個項目的幾毫秒內 `old/` 是空的，這時開始的排程不會被擋（#817）。
  - 設定裡沒有這個 id（舊的工作）、設定有問題、沒有勾選任務、存檔被擋下、執行器沒啟動、設定檔讀不進來：不跑，寫明原因，視窗留著。
  - 每次的結果寫在三個地方：`logs/schedule.log` 一行（本機時間與英文的 `[schedule] <id>: …`）、即時記錄一行、「定時執行」區最後一次的結果。開著的視窗 10 秒內沒接下第二次啟動時，第二次啟動自己在 `logs/schedule.log` 寫一行。
- 只在 Windows 上：定時執行需要 Windows 工作排程器。

## 13. 飾品清單（`gift_lists`）

商店買什麼、留什麼、賣什麼、拿什麼合成，由隊伍的 `gift_list` 指到的清單決定，取代版本 14 以前隊伍自己的 `keep_keywords`、`keywordless`、`keep_gifts`、`fusion_condition`。清單有兩種：開發者在資料檔提供、使用者不能改的「預設」清單（內容與位置見 [05-game-data.md](05-game-data.md)），以及存在設定檔的使用者清單，數量不限，可複製、可匯出入。（#291，2026-10-23 定案）

每個飾品在清單裡有三種狀態；沒列在 `want`、`keep` 的飾品就是 `drop`：

| 狀態 | 購買 | 當合成材料 | 出售 | 拿到後 |
|---|---|---|---|---|
| 想要 `want` | 買（只有商店可能賣的，I–IV 階，#626），被合成吃掉後再出現也再買；合成品則是商店買它缺的材料、湊齊就合成，到手後不再合 | 只當想要的合成品的配方材料（使用者 2026-10-30 決定）；一般合成不用 | 否 | 留著 |
| 保留 `keep` | 不買，想要的合成品缺它時除外 | 只當想要的合成品的配方材料（使用者 2026-10-30 決定：「想要」優先於「保留」）；一般合成不用 | 否 | 留著 |
| 不要 `drop`（預設） | 不買 | 可以 | 可以（受 `sell_max_tier`、`sell_vestiges` 限制） | 當材料或賣掉 |

第四種「鎖住」是派生的，不存檔：狀態是 `drop`、但它是某個「想要」而還沒持有的合成品的配方材料，有效狀態變成 `keep`；合成品到手後解鎖（使用者 2026-10-30 決定）。想要的合成品缺的材料（「不要」或「保留」）商店也會買，但狀態不變，見 [03](03-decisions.md) 第 13 節。GUI 上鎖住的飾品是虛線框、鎖頭，右上角有鎖住它的第一個合成品的圖示（被好幾個鎖住時加「+N」），滑過徽章寫「合成用（合成品名）：自動保留，商店會買。合成品到手後解除」。鎖住的飾品是商店賣的或合成品時，可以改標「想要」（其餘的不能標想要，只能取消那個想要）：「想要」是要飾品本身，被合成用掉後商店再出現會再買；改成「保留」或「不要」會被擋下（兩者的效果都等於保留），提示寫原因（使用者 2026-10-30 第三輪決定）。

| 欄位 | 鍵 | 類型 | 值 | 預設（空白清單） |
|---|---|---|---|---|
| id | `id` | 字串 | GUI 產生，不顯示；不能是 `default` | — |
| 名稱 | `name` | 字串 | 使用者自取，不重複 | 必填 |

- 飾品 id 存**數字 id**，不存名字：`gift_search.json`（Gift Search 頁的 327 個，I–III 階）、`gift_recipes.json`（61 個合成品、13 個 `gift_search.json` 沒有的配方材料，與 69 個 `extra_gifts`：不在 Gift Search 頁、配方也不用）和殘影 9991–9995（黯淡、微茫、閃耀、輝煌的殘影、月之殘影，階級 I–V）。
- 可以標「想要」的是商店可能賣的飾品與合成品（#626，使用者 2026-11-11 決定）。商店可能賣的是 `gift_recipes.json` 的 `shop.sells`：遊戲的飾品池（`mirrordungeon-egogift-droppool-8.json` 的 `egoGifts`）加上各主題包的專屬飾品池（`pack_gifts`；9205 WB Flask 不在 `egoGifts`，只在專屬池裡，實機 2026-10-22 看過它以 199 Cost 上架），扣掉全域排除（`globalExcludeEgoGifts`），扣掉圖鑑只寫一個取得條件「Shops - 「Fuse E.G.O Gift」」的飾品（`EN_MirrorDungeonEgoGiftLockedDesc.json`，1.118.1、1.119.0 都是 55 個），再扣掉所有合成品（月之記憶 9083 與 5 個主題包專屬合成品圖鑑沒寫只能合成，照樣當合成品）。1.119.0 有 372 個（1.118.1 是 366 個）：Gift Search 頁的 327 個，加上 45 個 IV 階（例如呼吸 IV 階的 Clear Mirror, Calm Water 9070：實機上架過 5 次）。其中 68 個（`shop.not_on_normal`，飾品池的 `excludeEgoGifts`）普通難度的樓層不賣：`excludeTargetIdxList` 是 `[0]`，對到 `mirrordungeon-08*.json` 的 `typeIndex`（普通 0、困難 1、無限 2、極限 3；程式本體沒讀到，是照欄位對出來的；實機在困難樓層看過 79 次，普通樓層 158 次裡一次都沒有）。Agent 在普通樓層的購買清單略過它們，所以它們不會讓普通樓層的商店刷新；不知道樓層難度時照樣列入。主題包專屬的飾品（`pack_gifts`）只在自己的主題包出現，GUI 的提示寫出是哪個包。每次上架的清單由伺服器挑選（`HttpRefreshShopEgoGiftsMirrorDungeonCommand`），客戶端看不到挑選方式。`extra_gifts` 以前不在清單裡，遷移與 GUI 都設不到，商店認出後一律當 `drop`：#310 的實機驗收裡，遷移後的呼吸清單把第 4 層合成出的 9070 在第 5 層當材料合掉；舊設定保留整個主要體系，所以現在照樣保留。名字會因中文化改變；id 換季時是否穩定、舊 id 會不會消失還沒驗證（同一季內 `gift_search.json` 的 320 個 id、體系、階級、英文名在 2026-10-16 與 2026-10-23 的版本完全相同；跨季沒有資料），所以載入時不認得的 id 不報錯：GUI 顯示警告並丟掉，Agent 靜默略過。（#291、#292）
- `gorder` 缺的飾品補在該體系最後（資料檔順序），多的 id（不是該體系商店可能賣的飾品）丟掉，缺的體系用預設順序；所以 `gorder` 不檢查是不是排列，換季後的舊設定仍可載入。（#292）
- `want` 裡出現殘影或商店不賣的非合成品不報錯：GUI 不讓選，Agent 的購買清單略過它們，因為資料檔換季後可能變動。（#292，未驗證換季時的實際情形）
- schema 檢查型別、`order` 的列舉與不重複（11 項）、`want`／`keep` 的不重複、`gorder` 的鍵是 11 個體系之一。跨物件檢查（GUI 與 Agent 各做一份，訊息一致）：清單的 id 或名稱重複（`gift_lists: id 'x' appears 2 times`）；隊伍引用不存在的清單（`teams/0/gift_list: team 'T' uses missing plan 'x' (not in gift_lists)`）；同一個 id 同時在 `want` 與 `keep`（`gift_lists/0: list 'L' has gift 9053 in both want and keep`）。（#292）
- 匯出是這份清單去掉 `id` 的 JSON（`name`、`order`、`want`、`keep`、`gorder`、`fusion_condition`）。匯入建立一份新清單：名稱加「（匯入）」、撞名加數字，不覆蓋現有清單；壞的或不認得的 id 略過並提示個數，同時在 `want` 與 `keep` 的留在 `want`，`order` 不是 11 個體系各一次就用預設，`fusion_condition` 不是三個值之一就用 `any`。（#292）
- **主要體系**：隊伍不再有自己的主要體系設定。主要體系是隊伍的 `gift_list` 指到的清單（「預設」是資料檔的預設清單，主要體系 `Burn`；2026-10-30 起它只放無體系飾品（2026-11-11 起另保留月之記憶的 10 個材料），`order` 沒變，所以主要體系照舊是 `Burn`）`order` 裡第一個不是 `Keywordless` 的體系。無體系排第一時它照樣最先買，但主要體系取下一個，因為初始飾品頁、定向刷新與合成的體系選單只有 10 個體系，沒有無體系。開局飾品的體系欄、事件選項的同級主體系優先、戰後選飾品的主體系優先、商店的定向刷新、一般合成的指定體系，GUI 觀測飾品挑選畫面的起始分頁，都讀這個主要體系。（#305）
