# 04 設定結構

本章定義使用者設定：設定檔放在哪裡、怎麼寫入與檢查，以及每一組設定的欄位，包括執行選項、出戰順序方案、星光方案、主題包方案、飾品清單、隊伍、事件覆寫與試煉分數覆寫；最後是 Agent 與 GUI 寫的其他檔案（`runs.jsonl` 等）。遊戲資料（主題包清單與預設方案、事件覆寫表、試煉表、選路權重）見 [05-game-data.md](05-game-data.md)。

## 1. 總則

- 使用者設定全部放在一份設定檔 `<root>/config/settings.json`，由自製設定 GUI（`gui/`，Tauri 2 + React/TypeScript）寫入，Agent 讀取。理由見 [ADR 0006](../adr/0006-settings-gui-writes-one-settings-file.md)。（#19，2026-10-14 定案）唯一的例外是隊伍佇列：Agent 在 bot 領到獎勵後把那一隊移到 `teams` 最後，只改順序（第 9 節「輪替」，[ADR 0011](../adr/0011-team-list-order-is-the-queue.md)）。
- PI V2 只保留控制器、資源與鏡牢任務，鏡牢任務沒有使用者選項。執行仍在 MXU 或 MFAAvalonia：PI 用 `agent.child_exec` 啟動 Agent，Agent 在任務開始時讀設定檔。（#6、#19，2026-10-14 定案）
- 第一階段（A1）的 GUI 只編輯設定，不執行 bot。之後 GUI 可能也負責執行（A2）；設定檔格式不得因此改變。（#19，2026-10-14 定案）
- 方案與隊伍數量不限，名稱由使用者自取。方案與隊伍各有一個 id，由 GUI 產生，不隨改名或排序改變；所有引用都用 id。（#19，2026-10-14 定案）
- `<root>` 是 Agent 的根目錄，用 Agent 程式的 `__file__` 定位，不依賴工作目錄，因為 MFAAvalonia 的獨立資料目錄模式下工作目錄不同。（#6）
- 設定 GUI 和 Agent 放在同一個發佈目錄，GUI 用自己執行檔所在的位置找到 `<root>`，不讓使用者選。（#19，2026-10-14 定案）
- 困難或普通、每週獎勵怎麼用這類策略都是設定。Agent 沒有狀態檔。（#8、#501，[ADR 0003](../adr/0003-screen-is-truth-state-file-only-rotation-cursor.md)）

## 2. 寫入與檢查

- 設定檔的格式由一份 JSON Schema `settings.schema.json` 描述，GUI 與 Agent 共用同一份。檔案位置在實作時決定。（#19，2026-10-14 定案）
- 設定檔有 `version` 欄位。格式改變時遞增版本，並提供遷移：GUI 讀到舊版本時遷移後寫回；Agent 讀到舊版本時在記憶體裡遷移，不寫回（移動隊伍佇列時也照舊版本寫回，只改順序）；讀到比自己新的版本就報錯。（#19）

  - 版本 20（#385）：執行選項新增 `target_floor`（整局目標層數，5／10／15），從版本 19 遷移時填 5，行為和以前完全一樣。Agent 目前只用它決定自動難度（見第 5 節）；入口與提示的行為之後再接。舊版 Agent 讀到版本 20 會報「比自己新」。
  - 版本 14（#291、#292）：商店留哪些飾品的設定從隊伍搬到飾品清單（第 13 節，#291、#292）。頂層新增 `gift_lists`；隊伍新增 `gift_list`，移除 `keyword`、`keep_keywords`、`keywordless`、`keep_gifts`、`fusion_condition`（主要體系改由清單決定，見第 13 節）。從版本 13 以前的檔案遷移時（版本 10 以前先照上面的步驟升到 13），每支隊伍產生一份清單，保留的東西完全相同的隊伍共用同一份（名稱用第一支隊伍的名稱，撞名加 ` 2`；id 是 `gift-list-1`、`gift-list-2`、…），隊伍的 `gift_list` 指向它。清單內容：
    - `order`：隊伍原本的主要體系第一，其餘照預設順序，`Keywordless` 最後，所以遷移後的主要體系和遷移前相同；
    - `want`：主要體系的所有可購買飾品（`gift_search.json` 裡該體系的 I–III 階）；
    - `keep`：主要體系與 `keep_keywords` 的其餘飾品（`gift_recipes.json` 裡該體系的合成品、配方材料與 `extra_gifts`；`keep_keywords` 體系的可購買飾品也是）、所有無體系飾品（`gift_search.json` 的 `Keywordless` 分頁與 `gift_recipes.json` 裡無體系的，含 `extra_gifts`）、`keep_gifts` 對得到 id 的飾品（用 `keyword`、`tier`、英文名對照 `gift_search.json`；殘影用名字對到 9991–9995）。已在 `want` 的不重複放進 `keep`。`keep_gifts` 對不到的丟掉並計數，GUI 遷移後在標頭的狀態列顯示「有 N 個對不到，已丟掉」，直到使用者改動設定或儲存；
    - `gorder` 用預設（每體系 III、II、I 階），`fusion_condition` 沿用該隊的值。

    遷移後的行為差異（Agent 已依清單買、賣、合成，這幾點是使用者會看到的）：

    1. 購買順序以前是「階級高到低、價格低到高」；現在是清單順序。遷移出的清單階級順序相同，但**同階內不再以價格低者優先**，改成資料檔順序。
    2. 無體系飾品遷移後一律 `keep`（使用者 2026-10-23 定案，不做第四種「只合成、不賣」的狀態）：不賣，**也不當合成材料**。舊的 `keywordless: keep` 行為不變；舊的 `fuse`（材料、不賣）與 `fuse_or_sell`（材料、可賣）都變成「不當材料」，這是**有損**的行為差異。
    3. 以前主要體系以外、不在保留名單的飾品一律是合成材料；現在它們是清單上的 `drop`（仍可當材料或出售），和「認不出是哪個飾品」的格子（保守地視為 `keep`）不同。殘影不算無體系飾品，只有 `keep_gifts` 名列的才進 `keep`，其餘仍是 `drop`，照舊當材料。
    4. 過渡期：購買（#298）、出售與一般合成（#299）、配方合成（#300）都已照清單做。這段期間不發版。
    5. Agent 不寫回設定，在記憶體裡遷移；GUI 讀到版本 13 以前的檔案遷移後寫回。舊版 Agent 讀到版本 14 會報「比自己新」。
- 只有 GUI 寫設定檔，Agent 不回寫。寫入必須先寫暫存檔再改名，避免寫到一半損毀。（#6、#19，2026-10-14 定案）
- 檢查分兩層。schema 負責結構檢查：（#19，2026-10-14 定案）
  - 型別、列舉值、數字範圍；
  - 出戰順序的罪人不重複（`uniqueItems`）；
  - 獎勵卡的 5 個順位不重複；
  - 星光的購買順序不重複。
- 跨物件的檢查 schema 表達不了，GUI 與 Agent 各自實作：（#9、#19，2026-10-14 定案）
  - 兩支啟用的隊伍指到同一個遊戲內隊伍欄位；
  - 隊伍的 `skill_replacement.sinners` 裡同一位罪人出現兩次，或某位罪人的 `target` 走不到：三個數字加起來不是 6、S1 超過 3、或 S3 少於 1（遊戲牌組是 3／2／1，每種換法都把一張牌往上換，S1 只會變少、S3 只會變多）；
  - 隊伍引用的方案不存在；
  - `run.target_floor` 大於 5 時（第 6 層起要求這一局每一層都是困難），每一支啟用的隊伍（輪替只用啟用的隊伍）的 `hard_from_floor` 必須是 1（關閉也不行），`usage` 不能是 `normal_only`；執行選項的難度也不能是 `normal`。錯誤訊息指出是哪一隊（`teams/<i>/hard_from_floor`、`teams/<i>/usage`、`run/difficulty`）。（#385）
  - 同一種方案或隊伍的 id 重複，或同一種方案的名稱重複；
  - 事件覆寫或試煉分數覆寫裡，同一個問題文字或試煉名稱出現兩次。
- GUI 在儲存時做兩層檢查，有錯就標出欄位，不寫入。Agent 在任務開始時重做兩層檢查，有任何錯誤就報錯並停止，不開始跑。（#9、#19，2026-10-14 定案）
- GUI 的問題清單用 GUI 的語言寫，點出隊伍、方案或飾品的名字和改法，例如「隊伍「Ta」、「Tb」都啟用，也都用 TEAMS #1：改其中一支的遊戲內隊伍欄位，或停用一支。」；Agent 的英文訊息原文（和 `agent/settings.py` 逐字相同）放在滑鼠提示。只有手改設定檔才會碰到的 schema 錯誤，在「請到設定檔修正」之後照錄原文。還沒按過儲存就有問題時，標頭的存檔狀態牌先寫「存檔前要修正 N 個問題」，儲存鍵換成紅框；欄位在第一次按儲存後才標紅。（#664）
- 有未儲存的變更時，存檔狀態牌旁有「放棄變更」：丟掉所有未儲存的變更，回到設定檔的內容；之後旁邊的「復原」把變更放回來，直到下一次編輯。（#664）
- 視窗不用系統的標題列：GUI 的標頭就是標題列，標頭的空白處與文字可以拖曳視窗、雙擊最大化，右上角是最小化、最大化／還原、關閉三個按鈕。關閉和 Alt+F4 一樣，有未儲存的變更時先問。視窗最小 800×480。（#664，使用者 2026-11-14 決定）
- 設定檔不存在時，Agent 視為沒有任何隊伍，報「先設定隊伍」。（#19）

## 3. 介面語言

- GUI 與 PI 都提供 `zh_tw` 與 `en_us` 兩種語言，預設 `zh_tw`。GUI 的語言存在設定檔的 `language`。PI 只剩少數標籤，`interface.json` 手寫，翻譯放 `interface_zh_tw.json` 與 `interface_en_us.json`。（#18、#19）
- 遊戲名詞保留英文原文，兩種語言都一樣：罪人名、體系、主題包、飾品、獎勵卡種類、試煉。只翻譯 bot 自己的說明文字。（#18）
- 例外是體系：`zh_tw` 的介面一律寫中文體系名（燒傷、流血、震顫……，`gui/src/i18n.ts` 的 `kw.*`），`en_us` 寫英文；設定檔仍存英文 id。（使用者 2026-11-14 決定）
- 例外是星光加成：`zh_tw` 的星光卡片以都市零漢化組（LLC）的中文名稱為主、英文名稱為輔，並列出該等級的效果文字（資料在 `gui/src/graces.json`，來源與授權見 NOTICE.md）；`en_us` 只顯示英文名稱。設定檔與 Agent 仍只用編號與英文名稱。（#52）

## 4. 設定檔的頂層結構

| 鍵 | 類型 | 內容 | 來源 |
|---|---|---|---|
| `version` | 整數 | 設定檔格式的版本 | #19 |
| `language` | 字串 | `zh_tw`／`en_us`，預設 `zh_tw` | #18 |
| `run` | 物件 | 執行選項，見第 5 節 | #8、#9、#14、#16 |
| `deployment_order_plans` | 陣列 | 出戰順序方案，見第 6 節 | #9 |
| `starlight_plans` | 陣列 | 星光方案，見第 7 節 | #9 |
| `theme_pack_plans` | 陣列 | 使用者的主題包方案，見第 8 節 | #11 |
| `gift_lists` | 陣列 | 使用者的飾品清單，見第 13 節 | #291 |
| `teams` | 陣列 | 隊伍，順序就是隊伍佇列，見第 9 節 | #9、#501 |
| `event_overrides` | 陣列 | 事件覆寫，見第 10 節 | #11 |
| `trial_risk_overrides` | 陣列 | 試煉分數覆寫，見第 11 節 | #17、#381 |
| `luxcavation` | 物件 | 日常的 Luxcavation 任務，見第 12 節 | #366 |

- 鍵名用 snake_case。（#19）
- 新的設定檔：各陣列都是空的，`run` 用下表的預設值。沒有隊伍，所以 Agent 會報「先設定隊伍」。（#19）

## 5. 執行選項（`run`）

03 與 06 章說的「全域」設定就是這一組。（#19）

| 欄位 | 鍵 | 類型 | 值 | 預設 | 來源 |
|---|---|---|---|---|---|

每個方案決定開局星光的購買計畫。數量不限。（#9，#19，2026-10-14 定案）

| 欄位 | 鍵 | 類型 | 值 | 預設 | 來源 |

| 各加成的等級 | `levels` | 陣列，10 項 | 第 i 項是加成 i 的等級：`none` 不買／`base` 基礎／`plus` +／`plus2` ++ | 全部 `none` | #9、#19 |
| 購買順序 | `priority` | 陣列，10 項，不重複 | 加成編號 1–10，排在前面的先買；GUI 依點選卡片的順序排列 | 1, 2, …, 10 | #9、#19 |
| 剩下的星光換成 Cost | `convert_leftover` | 布林 | 開／關 | 關（沒用掉的星光加進結算獎勵） | #9、#19 |

- 隊伍的「自訂」星光用同一組 `levels`、`priority`、`convert_leftover`。（#19）
- GUI 仿遊戲星光頁畫成 5×2 張卡片，每張卡四種狀態對應 `levels`：未選擇 `none`、已選 `base`、`+` `plus`、`++` `plus2`。（#52）
  - 點卡片本身：未選擇 → 已選（基礎）；已選（任何等級）→ 未選擇。
  - 點 `+`／`++`：選取並設成該等級；再點亮著的那顆回到基礎。和遊戲不同，未選擇的卡不保留等級。
  - 剛選取的卡排到已選的卡後面，取消選取的卡移到最後，所以購買順序就是點選的順序；卡片左上顯示它在已選卡片中的順位。
  - 右側的 `Select All Graces` 把未選擇的卡依編號選成基礎，全部已選時改為全部取消；`Enhance All` 的 `+`／`++` 把全部卡設成該等級，全部已是該等級時改回基礎。
  - 卡片右上顯示目前等級的價格（未選擇時顯示基礎價格），右側顯示合計。
- 加成依遊戲星光頁的順序編號，標籤用遊戲的英文名稱。（#9、#18）

| 編號 | 加成（英文名稱） | 基礎價格（星光） |
|---|---|---|
| 1 | `Star of the Beginning` | 10 |
| 2 | `Cumulating Starcloud` | 10 |
| 3 | `Interstellar Travel` | 20 |
| 4 | `Star-shower` | 20 |
| 5 | `Binary Star-shop` | 30 |
| 6 | `Moon Star-shop` | 30 |
| 7 | `Favor of the Nebulae` | 40 |
| 8 | `Starlight Guidance` | 40 |
| 9 | `Chance Comet` | 50 |
| 10 | `Perfected Possibility` | 60 |

- 編號依星光頁上排左到右、再下排左到右。名稱與基礎價格是 Mirror of Names and Spiders 這一季的實機畫面（實機：captures/03_starlight_page.png）。
- 「基礎」是卡片本身的效果，價格標在卡片右上；「+」「++」對應卡片底部的 `+`、`++` 兩個按鈕。（實機：captures/03_starlight_page.png）
- 點法與價格（2026-10-14 實機，Limbus 1.116.2，這個帳號 10 張卡都能用 `+`、`++`）：
  - 點卡片本身就是選取或取消選取這張卡，選取時卡片整張變白。
  - `+`、`++` 只設定這張卡的等級，不會選取它；再點亮著的那顆按鈕會回到基礎等級。卡片右上的價格跟著變成這個等級的總價。
  - 各等級的總價是基礎價格的 1／2／3 倍，10 張卡都一樣（例如 `Star of the Beginning` 10／20／30、`Perfected Possibility` 60／120／180）。
  - 選取時花的是卡片右上當下的價格，`Available` 立刻扣掉；改已選卡片的等級也會立刻反映差額。
  - 遊戲不擋買不起的卡：選了超過 `Available` 的卡，差額會從持有的星光扣，畫面變成 `Owned 4035-60`、`Available 0+60`（取消選取後恢復）。設定了的加成可以花持有的星光（#96）；所以買不起（`Available` 加 `Owned` 都不夠）要由 Agent 先用價格算好，點完再讀 `Available` 確認扣的和價格一致（出現 `+N` 表示 N 由持有的星光付）。
  - 連續點太快（間隔不到約 1 秒）會漏掉輸入。離開再回到星光頁時，選取與等級都重設。
- 可用的星光是星光頁右上的 `Available`，等於選隊頁該隊的 `Starlight Bonus`，不是持有的 `Owned`。「剩下的星光換成 Cost」對應星光確認對話框的 `Convert Starlight to Cost`；不換時，剩下的星光加進這局的結算獎勵。（實機：captures/01_team_picker.png、captures/04_starlight_confirm.png）
- 依購買順序購買。（#9、#19）
- 買不起（`Available` 加 `Owned` 仍不夠）時依執行選項「星光買不起時」處理：`skip` 跳過這張繼續買下一張，`stop` 停止整個任務：方案裡只要有一張買不起，就一張都不買，這局停在星光頁。買不起的加成不降級購買。（#9、#25）

主題包方案有兩種：開發者每季在資料檔提供的「預設」方案，使用者不能修改；以及使用者在 GUI 建立的方案，存在設定檔，數量不限。預設方案與這一季的主題包清單見 [05-game-data.md](05-game-data.md)。（#11、#19，2026-10-14 定案，[ADR 0006](../adr/0006-settings-gui-writes-one-settings-file.md)）

| 欄位 | 鍵 | 類型 | 值 | 預設 | 來源 |
|---|---|---|---|---|---|
| id | `id` | 字串 | GUI 產生，不顯示 | — | #19 |
| 名稱 | `name` | 字串 | 使用者自取 | 必填 | #19 |
| 分數 | `weights` | 物件 | 主題包英文名稱 → −10 到 10 的整數，越大越優先 | 空 | #11、#19、#240 |
| 刷新門檻 | `threshold` | 整數 −10 到 10 | 畫面上最好的包低於它就刷新 | 0 | #240 |
| 沒列出的包 | `unlisted` | 整數 −10 到 10 | 不在 `weights` 的包（新一季的包）和讀不出名稱的包的分數 | 0 | #240 |
| 活動卡包 | `event_packs` | 字串 | `weight` 照分數／`prefer` 優先選／`avoid` 避開；只作用在第 5 層最左邊、而且是活動劇情包或資料檔沒收錄的包的那一張（見 [03](03-decisions.md#6-主題包) 第 6 節） | `weight` | #240 |

- GUI 的樓層篩選是全部樓層加第 1–15 層，一排 16 個按鈕；另一排篩選是全部、普通、困難（[難度](../../GLOSSARY.md)）、無限、極限（第 6–10、11–15 層；`en_us` 寫 NORMAL、HARD、INFINITY、EXTREME，使用者 2026-11-14 決定）。第 1–5 層照資料檔的 `N`、`H` 逐層顯示；第 6–10 層顯示 `I` 的包、第 11–15 層顯示 `X` 的包（加上 `N`、`H` 清單裡有那一層的包），這兩段和 Agent 每層比對的包同一條規則（[05](05-game-data.md) 第 2 節；Agent 在第 1–5 層不分層，比對所有普通或困難的包）。選一排 0–15 而不依模式分組：使用者要看的是「第 N 層會出現哪些包」，樓層數字直接對到這一局的層數；分組時還得先選模式再選層。（#387）

- GUI（#240 設計稿 A）：每個用到的分數一欄，由高到低排列，0 欄固定保留；把主題包拖到別欄就改分數，拖到「＋」輸入數字建立新的一欄，點主題包也能直接輸入；欄裡沒有主題包就消失。刷新門檻是一條可以上下拖的線，停在兩欄之間，或最後一欄下方（不刷新），線上寫出門檻數字，門檻等於線上方那一欄的分數。活動卡包的選單旁寫明它只作用在第 5 層最左邊那一張，以及哪些包算數。上方用主題包名稱搜尋（按 `/` 跳到搜尋框，Esc 清除）、難度（普通／困難／無限／極限）和第 1～15 層篩選要顯示的主題包（依資料檔的樓層），只影響顯示。每張主題包的名稱右邊、同一行，用小標標出它出現的樓層。小標的底色是遊戲難度橫幅的顏色（#664，使用者 2026-11-14 決定）：黃底是普通、紅橙底加實線外框是困難、紫底加虛線外框是無限、紅底加雙線外框是極限，不靠顏色也分得出四種。小標裡只有樓層數字，例如資料檔的 `{N: [1, 2], H: [1]}` 顯示黃「1–2」紅橙「1」；連續的樓層寫成範圍，不連續的用頓號（紅橙「1、3」），某個難度沒有樓層就不顯示那個小標；`I` 顯示紫「6–10」，`X` 顯示紅「11–15」。主題包區塊頂部寫一次圖例：普通、困難、無限、極限（`en_us` 寫 NORMAL、HARD、INFINITY、EXTREME），後面接「數字＝會出現的樓層」。圖片模式的卡片同樣用小標，放在名稱下方；顏色走 `:root` 的 `--fl-*` 變數。小標帶 `aria-label`（難度加數字），不只靠顏色分辨。含想要的主題包另標一個琥珀色的「含想要」小標（#421，`small.wk`，顏色走 `:root` 的 `--wk-*` 變數）：標的是這個包專屬飾品池（[05](05-game-data.md) 的 `pack_gifts`）裡，用到這個方案的隊伍的飾品清單屬於想要類（想要，或想要的合成品還缺的材料）的飾品；滑鼠移上去的提示列出這些飾品的名稱（跟著 GUI 語言，如同 GUI 其他地方的飾品名），小標帶 `aria-label`。看的清單是用這個方案的所有隊伍各自選的清單（隊伍是否啟用都算，清單合在一起，只要有一份屬於想要類就標），沒有隊伍用這個方案時看預設清單；畫面不知道這一局拉到哪些包、持有什麼，所以材料照沒有持有算。小標只讀，不能點，也不改分數、不改 Agent 的選包；在飾品清單把專屬飾品改成想要之後，它所在的包立刻出現小標。活動劇情包在清單裡不另外標示（使用者 2026-10-22 決定）；活動卡包的開關與它的規則說明照舊。「名稱／圖片」切換：圖片是 #241 的封面縮圖，名稱一律顯示（有幾包共用同一張封面），沒有封面時顯示空白卡。
- 方案裡沒列出的主題包用 `unlisted` 的分數，例如新一季才出現的主題包；GUI 把這些包和「沒列出的包」放在同一欄，拖動「沒列出的包」就是改 `unlisted`。空的方案等於全部用 `unlisted`，不報錯。（#11、#19，2026-10-14 定案；#240）
- 隊伍只能選「預設」或使用者的方案，沒有隊伍專屬的自訂主題包標記。（#19，2026-10-14 定案）

規則：

- 出戰順序與星光可以引用方案，也可以選「自訂」，直接填只給這支隊伍用的值。把自訂的值存成方案、或從方案複製成自訂，由 GUI 提供。（#19，2026-10-14 定案）
- 「困難局從第 N 層起轉困難」只在這一局是困難局時有效。關閉時這隊打普通；只有執行選項的難度明確設成「困難」時以全域為準，整局每層都困難。難度是「自動」時，就算還有每週獎勵，輪到這隊的局也是普通局（`run_start.team_difficulty`；#137，2026-10-18 定案）。第 N 層之前用普通。任何一層選了困難後，之後都不能切回普通。普通局第 N 層（N > 1）能不能切到困難還沒實測；不能的話這個欄位會移除（[03-decisions.md](03-decisions.md#未決)）。（#9、#19）
- 獎勵卡比對不到任何類型時選第一張。（#11）
- 「存活少於 K 人時結束這局」的說明必須提醒：需要罪人陣亡的隊伍，治療方式應設為「不治療」。（#16）
- 0 有特殊意義、使用者看不懂的數字欄位，GUI 一律做成「開關＋數字」，關閉時數字欄反灰：限制局數、困難局從第 N 層起轉困難。單純 0 就表示「不做」的欄位（商店刷新上限、預留金額、全滅重打次數、存活少於 K 人）維持數字。（#137，2026-10-18 定案）
- 隊伍沒有試煉的權重：Boss 後的選擇評分是飾品分數 −（試煉分 + 0.36 × Enemy Level Up 的 N），每隊相同，1 pt 抵主要體系與其他飾品之間的 1 分（[03](03-decisions.md#12-選飾品boss-後的選擇與試煉)；版本 17 拿掉 `trial_risk_weight`）。（#17、#381）
- 開局連續防禦的做法、失敗時的退路與 Agent 重啟後的處理見 [03-decisions.md](03-decisions.md#8-戰鬥) 第 8 節。（#52）
- 觀測飾品花的是持有的星光；在 GUI 選了飾品就表示同意花費；遊戲一次最多觀測 3 個（觀測表只有 1／2／3 個的價格 70／160／270），所以清單最多 3 個：GUI 選滿後其餘飾品停用，schema 的 `gifts` 為 `maxItems: 3`，Agent 也以 3 為上限。舊設定超過 3 個時不默默丟掉，而是驗證報錯，使用者自己移除多的才能儲存（2026-10-16 使用者確認同意花費，#63）。選取規則見 [03-decisions.md](03-decisions.md#5-初始飾品與-gift-search) 第 5 節。（#54）
- GUI 的觀測飾品區塊預設收合，和遊戲的觀測頁一樣分體系分頁、III／II／I 三段；點飾品加到清單最後，再點一次移除，清單可拖曳排序。飾品列表是 `assets/resource/base/data/gift_search.json`（321 個）：清單、id、等級與英文名取自遊戲客戶端 1.118.1 靜態資料的觀測表（`tools/gift_search_table.py` 產生） `mirror-dungeon-egogift-observation-data-md8`（分頁順序即表的 `uiKeyword` 順序；表裡等級空白的用 `ego-gift*.json` 的 `TIER_n` 標籤補上；英文名來自 `EN_EGOgift_*` 在地化檔），依等級 III → I、表內順序排列；中文名依 id 取自都市零漢化組（LLC）的 release（`tools/llc_text.py`，見 `NOTICE.md`）。2026-10-16 實機逐格點過整頁對照：順序與等級一致，只有 5 個沒出現在頁面上（見 [02-screens.md](02-screens.md#ego-gift-search-頁的版面)）。換季時要依新的觀測表重新產生。（#54）
- 技能替換（#264、#454）：沒列的罪人、和目標是 3／2／1（遊戲原本的牌組）的罪人不換，所以清單空著就等於關閉，沒有全域開關。三種換法和價格（替換格 45／75／120 Cost；ID Skill Search 90／150／240 Cost 或 25／50／75 星光）是遊戲資料，放在 `data/shop.yaml` 的 `skill_replacement`（[05](05-game-data.md) 第 6 節），Agent 從那裡讀每種換法動哪兩種技能；要付的價格看對話框，以畫面為準；GUI 不標價格。付星光花的是持有的星光；在 GUI 選了 `starlight` 就表示同意花費。Agent 在商店照這份設定換技能（#455，[03](03-decisions.md) 第 13 節「換技能」）；`id_skill_search.enabled` 打開時，Super Shop 的 ID Skill Search 也照 `sinners` 的順序換一張，`pay` 決定付 Cost（遵守 `reserve_cost`）或持有的星光（不受 `reserve_cost` 限制）（#456，同一節「ID Skill Search」）。
- 技能替換要用哪些換法（#264 的規則，給 #455）：換法 a→b 只在技能 a 多於目標、技能 b 少於目標時才算。牌組從 3／2／1 開始，所以一個走得到的目標要用的換法是固定的：
  - S2 大於 2：`s1_s2` ×（S2 − 2）和 `s1_s3` ×（S3 − 1）；
  - 其他：`s2_s3` ×（2 − S2）和 `s1_s3` ×（3 − S1）。
  - 例：2／2／2 只要 `s1_s3` ×1；1／3／2 要 `s1_s2` ×1 和 `s1_s3` ×1；2／1／3 要 `s2_s3` ×1 和 `s1_s3` ×1。
  - `s1_s3_first` 只在要用兩種換法時有用：`true` 先試 `s1_s3`、再試另一種，`false` 反過來。bot 買第一個價格讀得到、付完不低於預留金額、而且遊戲讓它選（亮起來）的換法；一格只換一張。
  - 這張表只描述從 3／2／1 出發的設定；bot 每次都拿對話框讀到的 `Skills Owned` 套上面那條規則決定，不寫死這張表。Uptie 未滿 3 的人格讀到 `SKILL 3x0`、總張數 5，換到技能 3 的兩種換法是暗的，只剩 `s1_s2` 可能成立（#264）。
- 技能替換的 GUI（使用者 2026-11-06 採用的版面）：隊伍頁的商店區塊，預設收合，標題「技能替換」，整個區塊不顯示價格。
  - 只列要換的罪人。上方「＋ 加入罪人」選單列出還沒列的罪人，選了就加到最後、3／2／1；一位都沒列時寫「目前沒有罪人要換技能，全部維持 3／2／1。」。
  - 一位罪人一列，由上到下是優先順序，可以拖曳排序或用 ↑／↓；✕ 移除（改回不換）。每列有：S1（唯讀，= 6 − S2 − S3）；S2、S3 的 `− n +`，到極限的按鈕反灰，所以目標一定走得到（S1 0–3、S2 ≥ 0、S3 ≥ 1），沒有自由輸入的數字欄；狀態標籤，有變更時寫要用的換法（例「S1→S2 ×1、S1→S3 ×1」），還是 3／2／1 時寫灰框的「還沒變更」；換法順序選單，只在要用兩種換法時能選（「先換 S1→S3」或「先換 S1→S2」／「先換 S2→S3」），其他時候反灰、顯示「—」。
  - 手改設定檔造成走不到的目標（例 S1 4、總和 7），那一列框紅、狀態標籤寫哪裡不對，該列的 `− +` 和順序選單全部反灰，只能 ✕ 移除後重加；存檔時照 schema（張數不是 0–6 的整數）或交叉檢查報錯。
  - 列表下方：灰字「不換：」加上沒列的罪人；說明寫技能 3 要 Uptie 3 才有、換到的張數只在這一局有效。
  - 人格技能觀測（ID Skill Search，特殊商店）有開關和付款方式（Cost／星光），選星光時寫明花的是持有的星光。遊戲沒有官方中文，中文名取自都市零漢化組（LLC）`LLC_zh-CN` 的字串轉繁體：`MirrorDungeonUI_7.json` 的 `dungeon_shop_detect_personality_skill`（人格技能观测），說明裡的「替換○○的技能」是 `MirrorDungeonUI_2.json` 的 `dungeon_shop_upgrade_personality`（替换{0}的技能）。（#454）
- 刷新次數記在 Agent 記憶體，以層為單位，不存檔。（#10）
- 預留金額適用於所有花費：治療、換技能、購買、刷新。（#10、#19、#455）

### 輪替

- `teams` 的順序就是隊伍佇列。每一局由第一支啟用、用途符合這局難度的隊伍出戰；用途不符的隊伍跳過，留在原位。沒有任何可用的隊伍就以成功結束任務。（#9、#19、#364、#501）
- bot 看到某隊完成一局並領到獎勵後，Agent 重新讀設定檔，把那一隊移到 `teams` 最後再寫回，其他內容不動；放棄、停止，以及推不回隊伍的接續局都不動。啟用的隊伍因此依序各跑一局、循環下去。隊伍頁在清單上方說明這件事。（#501，[ADR 0011](../adr/0011-team-list-order-is-the-queue.md)）
- 使用者拖曳排序就決定下一局輪到誰。GUI 開著時 Agent 改了設定檔：GUI 每 2 秒、視窗回到前景與存檔前都重新讀檔；沒有未儲存的修改就直接採用新的檔案，有的話保留修改，再把 Agent 移到最後的隊伍也移到最後，所以存檔不會蓋掉 Agent 寫的順序。檔案被刪掉時保留編輯內容，存檔時重新寫入；開啟時沒有檔案、之後才出現的，以新設定檔為基準合併。GUI 與 Agent 寫入前都先確認檔案仍是自己上次讀到的內容，不是就重新讀檔再合併（[ADR 0011](../adr/0011-team-list-order-is-the-queue.md)）。狀態列顯示「設定檔在外部被改過，已重新讀取」或「設定檔不見了，儲存時會重新寫入」；存檔重試 3 次仍被拒（檔案一直被改動，或讀不懂），顯示「沒有儲存：設定檔一直在外部被改動，或讀不懂」，什麼都不寫。編輯中的隊伍被移走時，右邊仍顯示同一隊。（#501）
- 沒有任何啟用的隊伍不是設定檔的錯誤：只跑日常的人不必設隊伍。鏡牢任務開局時才檢查，沒有就以成功結束任務（回主畫面、記一筆 `no enabled team`，和「沒有可用的隊伍」同一條路，spec 06、#362），不報錯。（#364）
- 舊版的輪替游標（#501 之前，存在 `<root>/state/<控制器位址>.json`）在鏡牢任務開始時遷移一次：清單轉到游標那一隊排第一，然後刪掉所有狀態檔。游標指著停用或已刪除的隊伍時不轉。設定檔讀不到時狀態檔留到下次。（#501）
- 選隊頁顯示的隊伍和佇列選出的不同時，以畫面為準。（#8，[ADR 0003](../adr/0003-screen-is-truth-state-file-only-rotation-cursor.md)）

- 欄位名仍是 `trial_risk_overrides`／`risk`：版本 16 只改了值的意思與範圍，沒有改鍵名。（#381）

## 12. 日常的 Luxcavation（`luxcavation`）

GUI 的「日常」分頁編輯。要跑哪些日常、依什麼順序，由 MXU／MFAAvalonia 的任務清單決定（[ADR 0010](../adr/0010-one-pi-task-per-daily.md)），分頁上方寫明這點和建議順序。（#362、#366）

`exp` 是經驗本（PI 任務 `ExpLuxcavation`），`thread` 是紐本（`ThreadLuxcavation`，#368），兩個的欄位一樣：

| 欄位 | 鍵 | 類型 | 值 | 來源 |
|---|---|---|---|---|
| 模式 | `mode` | `daily`／`count` | `daily`（每日模式，預設）：打今天還沒打的，當天已贏的（手動打的也算）不再打；經驗本看通行證 Daily 的 `Clear EXP Luxcavation` 那一列，進行中打 1 場、完成不打；紐本看 Daily Bonuses，剩 n 次打 n 場；讀不到就不打；不用 `count`。`count`（自訂次數）：這次打贏 `count` 場，不讀今天打過幾場（經驗本不走通行證頁）（[spec 03 第 15 節](03-decisions.md)） | #429、#431 |
| 次數 | `count` | 整數 ≥ 1 | 只有自訂次數模式用：這次要打贏的場數。新檔與遷移的預設：經驗本 1、紐本 3（每天 3 次 Daily Bonuses，2026-10-27 使用者決定）。GUI 在每日模式把這格停用 | #366、#431 |
| 隊伍 | `team` | 字串或 `null` | `teams[]` 的 id：用它的遊戲隊伍編號、出戰順序和 `guard_turns`，不必啟用；`null` 是還沒選，任務開始時停止 | #366 |
| 戰敗重打 | `retries` | 整數 ≥ 0 | 每一場輸掉後重打的次數（打贏就重算，同鏡牢的全滅重打），預設 0 | #366 |
| 連戰 | `consecutive` | 布林 | 開（預設）：進場時把 Consecutive Battle 設成「剩下的場數，最多 10」，一場打完，一場 ×N 算 N 場；超過 10 就先 ×10 再開下一場打剩下的。關：一場一場打。剩下的場數是這個模式算出的場數還差的（#429、#431） | #375、#429 |

- 場數與 `retries` 由 #367 接上：打贏這個模式算出的場數結束，戰敗在 `retries` 內重打（[spec 03 第 15 節](03-decisions.md)）；戰敗訊號待截圖。

## 13. 飾品清單（`gift_lists`）

商店買什麼、留什麼、賣什麼、拿什麼合成，由隊伍的 `gift_list` 指到的清單決定，取代版本 14 以前隊伍自己的 `keep_keywords`、`keywordless`、`keep_gifts`、`fusion_condition`。清單有兩種：開發者在資料檔提供、使用者不能改的「預設」清單（內容與位置見 [05-game-data.md](05-game-data.md)），以及存在設定檔的使用者清單，數量不限，可複製、可匯出入。（#291，2026-10-23 定案）

每個飾品在清單裡有三種狀態；沒列在 `want`、`keep` 的飾品就是 `drop`：

| 狀態 | 購買 | 當合成材料 | 出售 | 拿到後 |
|---|---|---|---|---|
| 想要 `want` | 買（只有商店可能賣的，I–IV 階，#626），被合成吃掉後再出現也再買；合成品則是商店買它缺的材料、湊齊就合成，到手後不再合 | 只當想要的合成品的配方材料（使用者 2026-10-30 決定）；一般合成不用 | 否 | 留著 |
| 保留 `keep` | 不買，想要的合成品缺它時除外 | 只當想要的合成品的配方材料（使用者 2026-10-30 決定：「想要」優先於「保留」）；一般合成不用 | 否 | 留著 |
| 不要 `drop`（預設） | 不買 | 可以 | 可以（受 `sell_max_tier`、`sell_vestiges` 限制） | 當材料或賣掉 |

第四種「鎖住」是派生的，不存檔：狀態是 `drop`、但它是某個「想要」而還沒持有的合成品的配方材料，有效狀態變成 `keep`；合成品到手後解鎖（使用者 2026-10-30 決定）。想要的合成品缺的材料（「不要」或「保留」）商店也會買，但狀態不變，見 [03](03-decisions.md) 第 13 節。GUI 上鎖住的飾品是虛線框、鎖頭，右上角有鎖住它的第一個合成品的圖示（被好幾個鎖住時加「+N」），滑過徽章寫「合成用（合成品名）：自動保留，商店會買。合成品到手後解除」。鎖住的飾品是商店賣的或合成品時，可以改標「想要」（其餘的不能標想要，只能取消那個想要）：「想要」是要飾品本身，被合成用掉後商店再出現會再買；改成「保留」或「不要」會被擋下（兩者的效果都等於保留），提示寫原因（使用者 2026-10-30 第三輪決定）。

| 欄位 | 鍵 | 類型 | 值 | 預設（空白清單） |
|---|---|---|---|---|
| id | `id` | 字串 | GUI 產生，不顯示；不能是 `default` | — |
| 名稱 | `name` | 字串 | 使用者自取，不重複 | 必填 |
| 體系順序 | `order` | 陣列，11 項，不重複 | `Burn`、`Bleed`、`Tremor`、`Rupture`、`Sinking`、`Poise`、`Charge`、`Slash`、`Pierce`、`Blunt`、`Keywordless`；排前面的先買 | 如左（遊戲觀測頁的順序，`Keywordless` 最後） |
| 想要 | `want` | 陣列，不重複 | 飾品 id | `[]` |
| 保留 | `keep` | 陣列，不重複 | 飾品 id | `[]`；GUI 新增空白清單時 `want` 和 `keep` 都是 `[]`，所有飾品都是 `drop`（使用者 2026-10-30 決定：「新增保持全空，使用者如果需要可以用複製」，推翻 2026-10-29 的定案「新清單的無體系飾品不會被合成或賣掉」，當時是填入 116 個無體系飾品）。要從預設清單開始，用「複製這份清單」 |
| 飾品順序 | `gorder` | 物件：體系 → id 陣列 | 該體系內的購買先後，可跨階級；只影響「想要」的可購買飾品 | 每體系商店可能賣的飾品：IV、III、II、I 階，階內照資料檔順序（#626） |
| 合成條件 | `fusion_condition` | 字串 | `any` 材料夠就合（能升階的組合先合，再合出材料能做到的最高階）／`upgrade` 合出的階級比這組材料的最高階還高才合／`tier4` 只在能合出 IV 級時才合。階級由材料點數算出（[03](03-decisions.md) 第 13 節），不花星光；不合成的材料照一般規則仍可能被出售。GUI 的名稱（使用者 2026-10-22 定案）：任意合成／升階才合／只合 IV，英文 Any／Upgrades only／Tier IV only | `any` |

- 飾品 id 存**數字 id**，不存名字：`gift_search.json`（Gift Search 頁的 321 個，I–III 階）、`gift_recipes.json`（61 個合成品、13 個 `gift_search.json` 沒有的配方材料，與 66 個 `extra_gifts`：不在 Gift Search 頁、配方也不用）和殘影 9991–9995（黯淡、微茫、閃耀、輝煌的殘影、月之殘影，階級 I–V）。
- 可以標「想要」的是商店可能賣的飾品與合成品（#626，使用者 2026-11-11 決定）。商店可能賣的是 `gift_recipes.json` 的 `shop.sells`：遊戲的飾品池（`mirrordungeon-egogift-droppool-8.json` 的 `egoGifts`）加上各主題包的專屬飾品池（`pack_gifts`；9205 WB Flask 不在 `egoGifts`，只在專屬池裡，實機 2026-10-22 看過它以 199 Cost 上架），扣掉全域排除（`globalExcludeEgoGifts`），扣掉圖鑑只寫一個取得條件「Shops - 「Fuse E.G.O Gift」」的飾品（`EN_MirrorDungeonEgoGiftLockedDesc.json`，1.118.1 有 55 個），再扣掉所有合成品（月之記憶 9083 與 5 個主題包專屬合成品圖鑑沒寫只能合成，照樣當合成品）。1.118.1 有 366 個：Gift Search 頁的 321 個，加上 45 個 IV 階（例如呼吸 IV 階的 Clear Mirror, Calm Water 9070：實機上架過 5 次）。其中 68 個（`shop.not_on_normal`，飾品池的 `excludeEgoGifts`）普通難度的樓層不賣：`excludeTargetIdxList` 是 `[0]`，對到 `mirrordungeon-08*.json` 的 `typeIndex`（普通 0、困難 1、無限 2、極限 3；程式本體沒讀到，是照欄位對出來的；實機在困難樓層看過 79 次，普通樓層 158 次裡一次都沒有）。Agent 在普通樓層的購買清單略過它們，所以它們不會讓普通樓層的商店刷新；不知道樓層難度時照樣列入。主題包專屬的飾品（`pack_gifts`）只在自己的主題包出現，GUI 的提示寫出是哪個包。每次上架的清單由伺服器挑選（`HttpRefreshShopEgoGiftsMirrorDungeonCommand`），客戶端看不到挑選方式。`extra_gifts` 以前不在清單裡，遷移與 GUI 都設不到，商店認出後一律當 `drop`：#310 的實機驗收裡，遷移後的呼吸清單把第 4 層合成出的 9070 在第 5 層當材料合掉；舊設定保留整個主要體系，所以現在照樣保留。名字會因中文化改變；id 換季時是否穩定、舊 id 會不會消失還沒驗證（同一季內 `gift_search.json` 的 320 個 id、體系、階級、英文名在 2026-10-16 與 2026-10-23 的版本完全相同；跨季沒有資料），所以載入時不認得的 id 不報錯：GUI 顯示警告並丟掉，Agent 靜默略過。（#291、#292）
- `gorder` 缺的飾品補在該體系最後（資料檔順序），多的 id（不是該體系商店可能賣的飾品）丟掉，缺的體系用預設順序；所以 `gorder` 不檢查是不是排列，換季後的舊設定仍可載入。（#292）
- `want` 裡出現殘影或商店不賣的非合成品不報錯：GUI 不讓選，Agent 的購買清單略過它們，因為資料檔換季後可能變動。（#292，未驗證換季時的實際情形）
- schema 檢查型別、`order` 的列舉與不重複（11 項）、`want`／`keep` 的不重複、`gorder` 的鍵是 11 個體系之一。跨物件檢查（GUI 與 Agent 各做一份，訊息一致）：清單的 id 或名稱重複（`gift_lists: id 'x' appears 2 times`）；隊伍引用不存在的清單（`teams/0/gift_list: team 'T' uses missing plan 'x' (not in gift_lists)`）；同一個 id 同時在 `want` 與 `keep`（`gift_lists/0: list 'L' has gift 9053 in both want and keep`）。（#292）
- 匯出是這份清單去掉 `id` 的 JSON（`name`、`order`、`want`、`keep`、`gorder`、`fusion_condition`）。匯入建立一份新清單：名稱加「（匯入）」、撞名加數字，不覆蓋現有清單；壞的或不認得的 id 略過並提示個數，同時在 `want` 與 `keep` 的留在 `want`，`order` 不是 11 個體系各一次就用預設，`fusion_condition` 不是三個值之一就用 `any`。（#292）
- **主要體系**：隊伍不再有自己的主要體系設定。主要體系是隊伍的 `gift_list` 指到的清單（「預設」是資料檔的預設清單，主要體系 `Burn`；2026-10-30 起它只放無體系飾品（2026-11-11 起另保留月之記憶的 10 個材料），`order` 沒變，所以主要體系照舊是 `Burn`）`order` 裡第一個不是 `Keywordless` 的體系。無體系排第一時它照樣最先買，但主要體系取下一個，因為初始飾品頁、定向刷新與合成的體系選單只有 10 個體系，沒有無體系。開局飾品的體系欄、事件選項的同級主體系優先、戰後選飾品的主體系優先、商店的定向刷新、一般合成的指定體系，GUI 觀測飾品挑選畫面的起始分頁，都讀這個主要體系。（#305）
- 購買、出售、合成怎麼讀清單見 [03-decisions.md](03-decisions.md) 第 13 節。
