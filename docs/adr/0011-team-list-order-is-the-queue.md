# 隊伍清單的順序就是佇列，Agent 領獎後把那一隊移到最後

使用者想決定下一局輪到哪一隊（#501），但輪替游標存在 Agent 的狀態檔裡，GUI 看不到也改不了。#499 之後，使用者手動開、交給 bot 接續的局也算游標那一隊，使用者沒辦法修正。使用者 2026-11-08 決定照 AALC 的 `teams_active_queue` 做（[研究筆記](../research/aalc/10-mirror-dungeon-overview.md) 的「隊伍輪替」）：設定檔裡 `teams` 的順序就是隊伍佇列。每一局由第一支啟用、用途符合這局難度的隊伍出戰；bot 確認它領到結算獎勵，才把它移到清單最後（pop & append）。放棄、停止，以及推不回隊伍的接續局都不動順序。GUI 拖曳排序就直接決定下一局，不需要游標，也不需要另外的「下一隊」欄位。

## 資料形狀

- 佇列就是 `<root>/config/settings.json` 的 `teams` 陣列順序，沒有別的狀態。設定檔格式不變，不升版本。
- 選隊：第一支 `enabled` 且 `usage` 符合這局難度的隊伍。被跳過的隊伍留在原位。
- 寫回的時間點：Settle 看到 Claim 完成，而且知道這局的隊伍（`RUN["planned"]`）時。Agent 這時重新讀磁碟上的設定檔，因為 GUI 可能在這局中途存過檔。它只把這支隊伍移到 `teams` 最後，版本和其他內容照原樣，格式和 GUI 相同（縮排 2、不跳脫非 ASCII），先寫暫存檔再改名。隊伍已經在最後，或已經不在清單上：不寫。設定檔讀不到或寫不進去：記 log，下一局仍是同一隊。
- 和 GUI 同時寫同一個檔：GUI 記住自己最後讀到或寫入的檔案內容，每 2 秒、視窗回到前景、存檔之前各重新讀一次。內容變了：沒有未儲存的修改就直接採用；有的話保留修改，再把檔案裡被移到最後的隊伍也移到修改後清單的最後（`movedToEnd` 用最少次「移到最後」解釋兩個順序的差別）。所以使用者存檔不會蓋掉 Agent 的移動，使用者還沒存的拖曳也留著。剩下的空窗是 Agent 讀檔到改名之間的幾毫秒：GUI 剛好在這時存檔，那次存檔會被蓋掉。每局只寫一次，所以不加鎖。
- 舊狀態檔的遷移：鏡牢任務開始（TaskStart）時，`<root>/state/` 裡還有狀態檔，就用這個模擬器實例的游標把清單轉一圈，讓游標那一隊排第一，啟用的隊伍出戰順序和以前一樣。游標指著停用或已刪除的隊伍時不轉，以前那時也是從第一支開始。之後刪掉所有狀態檔，包括其他實例的：兩個實例共用一個帳號，現在也共用一個佇列。設定檔讀不到時狀態檔留著，下次啟動再試；轉完再跑一次不會再轉。

## Considered Options

- **保留游標，設定檔加 `rotation.start: {team, token}` 讓 GUI 指定下一隊**（#501 本文的建議 B）：GUI 只寫設定檔，Agent 只寫狀態檔，沒有共用的寫入對象。但下一隊仍藏在 GUI 看不到的狀態檔，每個實例一份，使用者要懂兩個概念。使用者選了佇列。
- **GUI 直接寫狀態檔**（#501 的 A）：GUI 要知道每個實例的位址，也違反 ADR 0006。
- **Agent 把佇列寫在自己的檔案，GUI 讀它**：只是把游標換個檔名，GUI 編輯的順序和實際的佇列又分成兩份。
- **照 AALC，隊首用途不符時也轉到隊尾**：不採用。使用者的決定是確認通關才 pop & append，所以只跑困難的隊伍不會因為一局普通局就被排到後面。

## Consequences

- 取代 [ADR 0003](0003-screen-is-truth-state-file-only-rotation-cursor.md) 的「狀態檔只存輪替游標」：Agent 不再有狀態檔。ADR 0003 的「中途接續以畫面為準」不變。
- 修訂 [ADR 0006](0006-settings-gui-writes-one-settings-file.md)：設定檔仍由 GUI 寫；Agent 例外地改寫 `teams` 的順序，而且只改順序。
- 接續的局（#436）從佇列推回隊伍。佇列只在領獎時變動，另外就是使用者在 GUI 改順序時：這局進行中改了順序，推回的可能不是這局實際用的隊伍，和中途改用途、啟用一樣。
- 以前兩個模擬器實例各有一個游標，現在共用一個佇列。
