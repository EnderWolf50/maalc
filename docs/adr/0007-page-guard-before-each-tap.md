# 長的自訂動作每次點擊前先確認還在自己的頁面

`MirrorHub` 每輪看畫面、交給對應的自訂動作（ADR 0002）。但有些動作一次會跑很久（商店一次造訪、事件的文字點擊、編隊、選禮物、戰鬥一回合），中途不再看是哪個畫面。2026-10-18 實機：商店造訪中使用者手動離開，`Shop` 繼續把地圖上的字當商品點了約 50 秒，打開 Boss 的節點面板，最後靠 L1 才回到正軌（#117、#118）。

決定：動作在每次點擊前用 `page_guard(context, <頁面節點>)` 確認畫面還是自己的頁面，不是就丟出 `PageGone`；動作的 `run()` 掛 `@hands_back`，接到 `PageGone` 就回傳 `True`，交回 `MirrorHub` 判斷新畫面。

- 頁面節點就是 `MirrorHub` 自己用來認出這個頁面的節點（`Shop`、`Event`、`Formation`、`BattleTurn`、`GiftChoice`…），不另外做新的辨識；之後這些節點換成更便宜的辨識方式，守衛跟著變快。
- 這些節點在自己頁面的對話框和子頁面上也會命中（`maatools.config.mts` 的畫面表、實機截圖）：商店的購買、出售、融合、關鍵字對話框都讀得到 Leave。唯一例外是商店的補血頁（沒有 Leave），所以 `Shop.heal` 只在按補血按鈕前檢查商店頁，補血頁裡的點擊不上守衛；造訪狀態在補血前就記為已補血，中途交回也不會付第二次。
- 沒命中時會在 1 秒內再看幾次：頁面淡入淡出或對話框掉下來時錨點會短暫消失。
- 全域彈窗（`Connecting`、`RetryPopup`、`PopupButton`）蓋在頁面上時，頁面節點仍讀得到（`maatools.config.mts`：`RetryCountdown.png` 上標題頁的節點照樣命中）。所以守衛先看這些彈窗，命中就當頁面已離開；`MirrorHub` 也是先處理彈窗再看頁面。
- 地圖的守衛也先看飾品獲得視窗（`COVERS`，`GiftGet`）：異想體戰之後它浮到地圖上時，右側按鈕（`MirrorMap`）照樣讀得到，`RouteMap` 在視窗下讀圖、拖了約 20 秒，報「找不到 Bus」走到 L2、L3（2026-10-21 實機兩次，#213）。`find_bus` 每次拖曳前也檢查。商店不列：`Shop` 自己關掉購買後的獲得視窗。
- 合成頁上第三列格子的說明框蓋住 Leave（2026-10-21 實機，#161），這時頁面節點讀不到。說明框讀到名字就是合成頁本身：先點空白處關掉再檢查；合成頁重開時留著的說明框，`Shop.close_tooltip` 改看頁面標題 `Fuse` 再點。#205 改成捲動列表讀格子，不再點開說明框，讀名字關說明框的路徑拿掉了；#331 又加回 `close_tooltip(context, page)`：先點 `TOOLTIP_CLOSE` 的空白處、再檢查頁面，用在放材料、讀格子（未認出的格子關掉說明框再讀一次）時。#378 起讀格子前先看截圖上有沒有說明框（`shop.tooltip`，紅色標題列）：有才點；沒有就直接用這張截圖檢查頁面，檢查不過（可能是沒看出來的說明框蓋住 Leave）再照舊先點、再檢查。放材料後、補讀未認出的格子時一律先點。
- `PlayTurn.guard` 的頭像點擊一批 0.1 秒一下，整批前檢查一次（用剛截的圖），不在每一下前各截一張。
- `Event` 的文字點擊每 0.15 秒一下（#174），每 `EVENT_READ_EVERY` 下才檢查一次，用上一次讀字時截的圖：`Event` 節點是 OCR，每一下都檢查會失去這個節奏。頁面離開後最多再點 `EVENT_READ_EVERY - 1` 下（離開到地圖時例外，見下面的 `ENDS_ON`），都落在什麼都沒有的左上角 (5, 5)。按下紅色按鈕後同一次呼叫接著點（#188），按鈕還亮著的淡出畫面照點，第一張不亮的畫面先讀字再點下一下；淡出時紅色先暗掉、字還讀得到的話，事件結束後一樣最多再點 `EVENT_READ_EVERY - 1` 下。（#188，使用者 2026-10-21 決定）
- 事件的守衛反過來放過飾品獲得視窗（`TAPPED_THROUGH`，`GiftGet`）：事件給飾品時，GET! 視窗浮在淡出的事件頁或事件結束後的地圖上，文字點擊點在左上角就會關掉它。#309 的錄影裡，6 個視窗（5 個單飾品、多飾品的第一個）都在一下角落點擊後 0.1–0.2 秒消失，期間 bot 沒送別的點擊；沒被點的那個停了 1.8 秒。原本守衛不認得視窗，沒命中就再看 1 秒、這段時間不點，多飾品事件的第二個視窗停 1.7–2.5 秒，交回後才由 `GiftGet` 按 Confirm。地圖不一樣：地圖的動作不點視窗，所以交給 `GiftGet`（`COVERS`）。
- 事件結束在地圖上（`ENDS_ON`，`MirrorMap`）：事件的守衛在事件頁和 GET! 視窗之後找 `MirrorMap`，看到就丟 `PageEnded`（`PageGone` 的一種），不再看 1 秒。原本地圖上守衛沒命中，再看 1 秒才交回，最後一下角落點擊後 1.4–1.6 秒（#511）。`GiftGet` 排在前面，因為視窗蓋在地圖上時 `MirrorMap` 也命中（`GiftGetOverMap.png`）。地圖也會短暫出現在第一個視窗之前和兩個視窗之間，所以 `Event.advance` 接到 `PageEnded` 時照樣點角落，等畫面從那張截圖起沒再變、且已靜止 `EVENT_MAP_REST`（0.4 秒）才交回；靜止是看每下點擊後截圖的縮圖（`recovery.same_screen`）。2026-10-23 的視窗錄影（28 個事件結尾）：視窗出現前（第一個或第二個），地圖最多靜止 0.23 秒；最後的地圖在出現後 0–0.27 秒內停下來。按鈕標籤區在有些地圖上也讀空（`MapCostFloor3.png`），所以 `advance` 讀到空的、而畫面是地圖時不停，交給守衛。
- `PlayTurn` 交回 hub 不算一次送出：同一回合的送出次數只在真的按過 START 後才累計。
- 交回 hub 後，hub 會再把同一個頁面交給同一個動作；動作本來就以畫面為準（ADR 0003），重新進入是安全的，只多花一次 hub 的判斷時間。

## Considered Options

- **(a) 動作每次只做一步就回 hub，狀態放在 `RUN`**：不採用為主要做法。要把每個長流程拆成可以中斷、接續的狀態機，改動大。長流程之後再逐步往這個方向拆。
- **(b) 點擊前的頁面守衛**：採用（使用者 2026-10-18 決定）。
- **只看「是不是跑到地圖」這類反向判斷**：`Shop.to_main` 原本就是這樣。只抓得到已知的離開方式，抓不到彈窗、斷線或回到主選單，所以守衛改成正向確認自己的頁面。`ENDS_ON`（#511）不取代正向確認：守衛先看彈窗和自己的頁面，都沒命中才看結束頁，認出來就不必再看 1 秒；其他沒命中的畫面照舊。

## Consequences

- 每次守衛多一次截圖與四次辨識（三個彈窗節點加頁面節點；彈窗節點先比模板，沒命中就不讀字；地圖多一次 `GiftGet` 的讀字，事件頁沒命中時也多一次；事件的守衛在事件頁和視窗都沒命中時再比一次 `MirrorMap` 的模板）。點擊本來就要等畫面反應，額外時間相對小。`Event.advance` 每下點擊多算一次截圖縮圖（#511）。
- 進入地圖上的新節點時清掉 `RUN["shop"]`：沒按 Leave 就離開的商店，下次進商店會是一次新的造訪。
- `RewardCard` 每輪用守衛確認頁面（標題會穿透彈窗，所以不只看標題）；`Settle` 按下 Claim 後的迴圈原本就每輪確認標題，不另外加守衛。
