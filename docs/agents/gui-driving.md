# Driving the settings GUI with cua-driver

What `cua-driver` needs to operate the Tauri settings app (`gui/`) on Windows. Each fact names its source: `[run]` is the run of 2026-10-30 with `cua-driver 0.38.0` on Windows 11, `[second run]` a later run that day on the same setup (a check of the guard-turns note), `[third run]` a run of 2026-10-31 on the same setup (a check of the trial notes and the teams tab), `[cua docs]` the installed cua-driver skill (`~/.claude/skills/cua-driver/`) or `cua-driver describe <tool>`, `[retro]` a finding of the 2026-10-30 retro over agent sessions of 2026-10-16 and 2026-10-17, `[devtools run]` the run of 2026-11-14 that built `tools/gui_devtools.mjs` (#747; WebView2 157.0.4341.46, Windows 11, display at 150 %), `[#745 run]` the check of PR #745 the same day, `[#815 run]` the check of #815 on 2026-11-17 (the same setup), `[#743 run]` the check of #743 on 2026-11-22 (the same setup, cua-driver driving the window in background delivery), `[#916 run]` the check of #916 on 2026-11-23 (the same setup). The `maalc-gui-check` skill is the procedure; this file is what it relies on.

## cua or DevTools

Two ways act on the window, and they prove different things:

- **cua-driver, background delivery**: what a user's click, typing, select or scroll does. Its input goes to the window through Windows, as a user's would, and leaves the user's cursor and focused window alone. Use it for every control a user clicks. [cua docs WINDOWS.md `delivery_mode`]
- **`tools/gui_devtools.mjs`**, over the page's DevTools port: what cua's background delivery cannot do. A press held for a time, a drag-and-drop, keys with modifiers (Shift+Tab), the light or dark scheme, the page at another size (800 × 480), an element's box, a still of the page with the header's path blacked out, the accessibility node, the console. Its input enters the page (Chromium's own input path), not the window: it never touches the user's cursor, and it does not prove what the window itself does (its frame, the title bar's drag region, a system key): Alt+F4 sent this way reached the page and left the window open. A still of the window with its frame is cua's `get_window_state`. [devtools run]

A cua click on a tab (the pixels come from the latest `get_window_state` screenshot):

    cua-driver call click '{"pid":<pid>,"window_id":<hwnd>,"x":316,"y":116,"delivery_mode":"background","session":"<task>"}'

The same window over DevTools: `open` holds it in the background and prints `{"pid", "hwnd", "port", ...}`, then each command acts on the page at that port (`--help` lists them all):

    node tools/gui_devtools.mjs open --root <main checkout>/.local/scratch/<task>/gui-root     (a background command)
    node tools/gui_devtools.mjs drag "js:[...document.querySelectorAll('aside li')][0]" "js:[...document.querySelectorAll('aside li')][1]" --port <port> --then "[...document.querySelectorAll('aside li .item')].map((i) => i.textContent)"

What the run of `tools/gui_devtools.mjs` showed:

- The app reads `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` and `WEBVIEW2_USER_DATA_FOLDER`: the browser process ran with Tauri's own `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection` and the added `--remote-debugging-port`, on the root's `webview2` folder. A data folder of its own keeps the port from being lost to another WebView2 of the same app. [devtools run: the command line of `msedgewebview2.exe`]
- The `hwnd` that `open` prints is cua's `window_id`. [devtools run: `list_windows`]
- `--viewport 800x480` lays the page out as a real 800 × 480 window does: the team page and the 星光方案 tab scrolled to the second row of cards gave #745's numbers to the hundredth of a pixel, which came from the window resized with cua's `set_window_frame` (1204 × 724 at 150 %, `innerWidth` 800, `innerHeight` 480). A cua still taken meanwhile shows the page drawn at the window's top left and the rest blank. [devtools run; #745 run]
- An emulation (scheme, viewport, forced `:hover`) lasts while its DevTools session is open, and other sessions see it: `scheme light --viewport 800x480` left in the background made a second command read 800 × 480 and the light scheme, and a cua still showed it; stopping it brought back 1500 × 860, dark. [devtools run]
- Stopping the `open` command (a background task's stop, `taskkill`) ended the app and its WebView2 with it: libuv puts a child that is not detached in a job killed with its parent (`src/win/process.c`), and the WebView2 processes ended with their app. The app's own close button ended the `open` command. An app that `tools/gui_probe.py` had left on the root was stopped by the next `open` there. [devtools run]
- A DevTools drag intercepts Chromium's drag (`Input.setInterceptDrags`) and dispatches the drag events at the target, so the page's hit testing picks where it lands; it does not go through Windows' drag-and-drop, which a Tauri setting broke once (`dragDropEnabled`, #64): a build with `"dragDropEnabled": true` still reordered the team list under a DevTools drag. That setting stays covered by `gui/src/dragSort.test.ts`. [devtools run]

## A live run from the window

`tools/live/gui_run.py` drives a live run from the window (the `maalc-live-test` skill, "From the settings window", has the steps). What it rests on, from the runs of 2026-11-18 (#811's checks) and of 2026-11-20 (#835's tools):

- `open --root <install>` starts that folder's own exe on its own settings with the DevTools port and WebView2 folder of the first point above; `gui_devtools.mjs open` lays a root out again with demo settings, so it is for a throwaway root only. It refuses the main checkout's `install/`, a folder some maalc-gui.exe already runs from (the app keeps one window per folder, `src/instance.rs`), and a page that does not render. It holds the app in a Windows job, so stopping it ends the app and its WebView2: on 2026-11-20 a `taskkill /F` of the holder alone (no `/T`) left neither running. [#835 run]
- The window's title is `maalc` and screen-record's `--window` takes the largest window whose title holds the substring: on 2026-11-20, six visible windows held "maalc" (the agent's, a browser's, Explorer's, the user's own settings window and two test windows), the window to record among the smaller ones. `open` sets the title to `maalc-live-<port>` with `SetWindowTextW` (the app never sets it again) and `record --hwnd` checks that one window holds it, then that the recording's state names that hwnd; it recorded the 640 × 400 test window of the two titled "maalc" and nothing of the larger one. `title` refuses the user's own window (the app running from the main checkout's `install/`). [#835 run; #811's checks of 2026-11-18]
- `start`, `stop` and `state` read and press the Run tab over DevTools: `.runner-status` and its `data-phase` (idle, running, stopping, ended), each `.task-list .task-row` (its task id in `data-task`, its run state in `data-state`: absent before a run, `off` on a row the run left out, so the run's tasks are the rows with another value, in the list's order; its name `.tr-name`, its reason `.tr-reason`), the alerts (`.run-notes p`, the crash's `.crash[role=alert]`, its last lines too); Start is `.runner-bar button.primary`, Stop the bar's second button (`gui/src/Run.tsx` `RunControls`, `TaskList`, `RunLog`). The wide and the narrow window draw them with the same classes. `gui/src/runner.test.tsx` runs `gui_run.py`'s own script against both, so a markup change fails there. A DevTools press proves what the page does with the press; a check of the click itself is cua's. [#835 run: `state` read "no task ticked" and Start disabled; `start` refused with that reason; #880 run on the redesigned page: `state` read the same, then the ticked task's `failed` and its reason from the test runner]
- The settings window paints only when its page changes, so a recording of it has stretches with no new frame (13 s in the #835 run, up to 78 s in #811's checks): screen-record warns, and the clip holds the last frame. [#835 run; #811's checks]

## Build and launch

- The GUI has its own lockfile: `pnpm --dir gui install --frozen-lockfile` before the first build in a worktree (`docs/agents/local-dev.md` "New worktree" installs only the root's). `pnpm --dir gui tauri build --no-bundle` takes about 3 minutes cold and writes `gui/src-tauri/target/release/maalc-gui.exe`. [run]
- The exe reads and writes `<folder of the exe>/config/settings.json` and looks for `resource/` or `assets/resource/` beside it (`gui/src-tauri/src/lib.rs`, `root` and `data_dir`). Launching it from `target/release/` finds neither, and launching it from `install/` edits the real settings. `tools/gui_probe.py` copies the exe into a throwaway folder with demo settings and a link to `assets/`. [lib.rs]
- The window reads its game data and images from that `resource/base/data` at run time (#767): its images go through Tauri's asset protocol, open to that one folder (`lib.rs` `setup`), and no game data is in the exe. To check a data change without a build, lay out a root with `tools/gui_probe.py --prepare-only`, copy `assets/resource/base/data` to `<root>/resource/base/data` (`resource/` is found before the `assets/` link), edit the copy, and start the copied exe yourself: `gui_probe.py` and `gui_devtools.mjs open` lay the root out again (a `resource/` made before is gone). A file the window needs and cannot read makes it show the reason in place of the page (`StartError.tsx`). [#767 run]
- The demo settings are the `valid` case of `tests/settings_cases.json` (`language` is `zh_tw`; a retro report notes that `en` is not a valid value and `en_us` is). [run; retro, 2026-10-17]
- The window title is `maalc` (`gui/src-tauri/tauri.conf.json`, `app.windows[0].title`), and it is the top-level window of the exe's own pid, so `tools/gui_probe.py` finds it by pid and title. [run]
- The header of the app shows the full path of `settings.json`, a local path. Black it out of every screenshot before it is attached to a public issue or PR. [run: visible in the first screenshot]
- Stop the app by the pid the probe printed: `taskkill /T /F /PID <pid>` (PowerShell; Git Bash rewrites `/T` into a path). The process has WebView2 children, so `/T` is needed. cua's `kill_app` was refused in standard permission mode. [run; retro]

## Seeing the window

- The order numbers' contrast on the deployment cards: `uv run python tools/number_contrast.py --port <port>` (the port `gui_devtools.mjs open` printed) holds each number over white art against the ring 1–2 CSS px out, its median and 90th percentile, at 1500 × 860, 1280 × 720 and 800 × 480 in both schemes. [#756]
- `get_window_state` with `include_accessibility_tree:false` returns a screenshot of that one window plus its bounds; `--screenshot-out-file <png>` on `cua-driver call` saves it. It never captures the screen. `get_desktop_state` captures the whole display: not for a GUI check. [run; cua docs `describe get_window_state`]
- Sizes differ by setup: the window is 1500x860 in `tauri.conf.json` (1100x760 before #732, 1500x760 before #741); in the [run], `list_windows` reported 1654x1187 and the screenshot was 1455x1044. Action coordinates are pixels of the latest screenshot, not window or screen pixels. A retro report names 1620x1500 for another setup: read the sizes again each run. [run; retro]
- Each `cua-driver call` is a session of its own. A `drag` or `click` needs a `get_window_state` of the same window in the same session first, else it fails with `screenshot_context_missing` / `window_never_read`. Pass the same `"session":"<name>"` to every call (read, then act, then read), or put the steps in one `run_script`. [run]
- The page is a WebView2: the first tree read showed only the title bar (5 elements), a later one 138 elements with a `Document` node. Act by pixel off the screenshot and judge by the next screenshot. [run]

## Input

- Background delivery is the default and the cua docs ask to try it first; the driver says by `background_unavailable` when it cannot. [cua docs `describe drag`, WINDOWS.md "Always try `delivery_mode:"background"` first"] Two retro sessions got `Background delivery is not available for target window class 'Tauri Window'` for `mouse_scroll`, and fixed it with `delivery_mode:"foreground"`. [retro, 2026-10-16]
- A click on a tab went through in background mode. [run]
- A drag reported `effect: "unverifiable"` every time, whether the list moved or not: only the next screenshot tells. [run]
- Drag-and-drop that moved: `delivery_mode:"foreground"`, `duration_ms:4000`, `steps:120`, on the team list in the left column (Team a dragged below Team b; both swapped, "有未儲存的變更" appeared). The retro report says a 1 s drag fired the events but did not reorder (not repeated here). A drag of 1 s with 20 steps in background mode on a deployment card did nothing: those cards are click-to-order, not draggable. No background drag has been tried on a sortable list yet; background delivery answers `background_unavailable` for event kinds it knows it drops, Chromium DOM mouse among them, and the page is a WebView2 (Chromium), so expect that answer for a drag. The foreground drag above came before the user's yes was needed for it (next point). [run; retro, 2026-10-17; cua docs WINDOWS.md `delivery_mode`]
- Foreground delivery is SendInput with a brief `SetForegroundWindow`: it can move the physical cursor and fronts the window for the length of the action, and restoring the previous foreground is best-effort. It takes the cursor from whoever is using the machine, so the `maalc-gui-check` skill runs it only on the user's yes to that action (the user, 2026-11-08). [cua docs WINDOWS.md `delivery_mode`, RUNTIME.md "Foreground boundary"]
- Scrolling the settings page did not work in a second run on 2026-10-30 (cua-driver 0.38.0, Teams tab, to reach the note under the guard-turns field): `scroll` of 10 ticks in background delivery and 15 in foreground, `press_key end` after a background click on the page, and a foreground `drag` of the page's scrollbar; after each, the next screenshot showed the page still at its top. This differs from the retro report above, where foreground delivery fixed `mouse_scroll`. Resizing the window with `SetWindowPos` without activating it left the WebView2 area blank, and the app was restarted. That run could not look at a control below the fold. [second run]
- What does scroll the page: a background `click` on the page's scrollbar track, at the right edge of the screenshot (x 1443 of 1455), pages down below the thumb and up above it; a click on the arrow at either end moves a few lines. A run on 2026-10-31 (cua-driver 0.38.0, Teams tab) reached the bottom of a team and came back to the top this way, after `scroll` in background (`background_unavailable`), `scroll` in foreground and Ctrl+minus in foreground had left the page where it was. [third run]
- A `<select>` changes in background delivery: a `click` on it focuses it, then `press_key` `escape` and `up` / `down` step to the next option, and the next screenshot shows it (the heal method and the language select, 2026-10-31). [third run] On the Run tab's scan pick, `down` moved the shown option but the page took it only after a `return` (an open list commits on Enter). [#815 run]
- A background `click` by pixel is not always a mouse click: cua first asks UIA for the element under the point and, when it finds one that takes Invoke, invokes that instead (`route: accessibility`, "Performed UIA Invoke"). A task's tick on the Run tab is a `CheckBox`, which takes Toggle, not Invoke, so a pixel click on the box invoked the row's `ListItem`: the row was picked and the tick stayed as it was, what #814 saw. The first pixel click of the run, before anything had read the tree, posted mouse messages (`route: synthetic_events`) and ticked it. Tick it by the `CheckBox`'s element token (cua performs UIA Toggle) or the tick area's `Group` token (UIA Invoke on its `<label>`); DevTools `press` on the box or on the area around it ticks it as a real mouse does. [#815 run]
- A click with Ctrl or Shift held cannot go through background delivery: cua refused `click` with `modifier:["ctrl"]` and `delivery_mode:"background"` (`click modifiers require delivery_mode:"foreground" on Windows; UIA and PostMessage cannot carry live modifier-key state`). `gui_devtools.mjs press <target> --with Ctrl` (or `Shift`, `Ctrl+Shift`) holds them through the press's mouse events, and the page read them as the click's `ctrlKey` and `shiftKey`: four theme packs picked by a Ctrl press each, a range picked by a Shift press. A `--move` with a negative number takes `=`: `--move=-400,45`. [#743 run]
- A drag, a held press or a key with modifiers that background delivery cannot send goes through `tools/gui_devtools.mjs` ("cua or DevTools" above), not foreground delivery. A team dragged onto the next one there reordered the list and showed "有未儲存的變更"; a press on a team moved 40 px while held reported the drag the page started and cancelled it. [devtools run]
- A drag held at a point goes through `drag <from> [<to>] --via X,Y:MS`: it stays there MS ms, dragover sent again every 100 ms (the HTML standard has a browser repeat it every 350 ± 200 ms while a drag lasts, [its drag-and-drop processing model](https://html.spec.whatwg.org/multipage/dnd.html#drag-and-drop-processing-model)), and `--watch <expression>` prints a value meanwhile (the page's `scrollTop`). The drag starts at the press on `<from>`, which the page takes as where it was picked up: a `<from>` inside an edge zone makes the page wait until the pointer goes nearer that edge or leaves the zone (`gui/src/dragScroll.ts`). A `<to>` the tool had to scroll into view prints `"scrolled": true`: the page did not bring it there. Before #916's fix, a pack held in the air scrolled the page only within about 20 px of its edge (Chromium's own drag autoscroll: 8 px from the bottom, 0 to 1362 in 5 s), and not at 30 px from the bottom, 35 px from the top, or on the tab bar above the page. [#916 run]
- `set_window_frame` resized the window to 800 × 480 logical (1204 × 724 at 150 %) and the page stayed drawn, unlike the `SetWindowPos` above; `gui_devtools.mjs --viewport 800x480` gives the same layout without resizing the window. [#745 run; devtools run]
- Which controls take a drag: the sortable lists (`gui/src/ui.tsx`, `li draggable`) and the theme pack chips (`gui/src/ThemePacks.tsx`). The theme pack lanes also take a box drawn from empty space (`gui/src/packPicks.tsx`), from pointer events, not HTML5 drag and drop: `press <x,y> --move=DX,DY` draws one, and its point must be empty space in the lanes, not a pack. [#743 run] The setting that breaks them is `dragDropEnabled`: Tauri's default swallows HTML5 drag-and-drop on Windows, so it stays `false` in `tauri.conf.json` (commit 380aad8, #64). [git log 380aad8; retro]

## UIPI and elevation

A process at a higher integrity level than the driver refuses its input: AALC self-elevates through `pyuac`, and cua reported `UIPI: target hwnd … is at High integrity`. The settings GUI launched by `tools/gui_probe.py` runs at the integrity of the shell that launched it and took input in the run above; if a future shell is elevated and the driver is not, expect the same refusal. [retro, 2026-10-16; run for the GUI]
